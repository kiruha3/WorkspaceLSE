# Автономная установка Windows x64 — 30.10.2026

Предыдущий комплект содержал установщики инструментов, но загружал библиотеки из сети. По поручению владельца готовый ZIP теперь включает зависимости и устанавливается автономно.

## Состав и поведение

- Пять прежних установщиков из `installation/packages.json`.
- `installation/offline/python/requirements.txt`, экспортированный из зафиксированного `backend/uv.lock`, и **16 wheel-файлов** для Windows x64/Python 3.13.
- Отдельный npm-кэш, подготовленный для `frontend/package-lock.json` в изолированной папке, без изменения работающего `frontend/node_modules`.
- **18 файлов зависимостей**, привязанных контрольными суммами к lock-файлам: 16 wheels, requirements и `npm-cache.tgz`. Внутри npm-архива — **300 обычных файлов кэша**, без логов и пользовательской конфигурации. LF и CRLF нормализуются при проверке идентичности lock-файлов.
- Установщик вызывает только проверку локальных инструментов; загрузка файлов доступна отдельному подготовительному скрипту, а не ветке установки.
- Python: `uv venv --offline --no-cache`, затем `uv pip sync --offline --no-cache --no-index --find-links ... --require-hashes`.
- npm: `ci --offline --ignore-scripts --no-audit --no-fund` с копией комплектного кэша в `.runtime/npm-cache`. Исходный кэш дистрибутива остаётся неизменным.
- Миграции, начальные справочники, bootstrap и сборка выполняются после установки зависимостей.

## Проверки

1. `installation/Test-OfflineAssets.ps1`: **6 проверок** — отсутствующий манифест, корректный комплект, LF/CRLF, изменённый lock-файл, отсутствующий файл, повреждённый файл.
2. `Install.ps1 -CheckOnly` проверил пять установщиков и все 18 файлов библиотек без установки.
3. В свежей копии проекта временно убран один wheel. Обычный `Install.ps1` завершился ожидаемым отказом **до создания** `backend/.venv` и каталога PostgreSQL; файл восстановлен.
4. Полная свежая установка проверена в отдельной папке без `.venv`, `node_modules` и схемы БД. Для процесса заданы недоступные прокси `http://127.0.0.1:9`, новые пустые внешние кэши uv/npm, `UV_NO_CACHE=1`, `UV_OFFLINE=1`, `NPM_CONFIG_OFFLINE=true` и пустые пользовательский/глобальный npm-конфиги. Loopback оставлен доступным для локальной PostgreSQL.
5. Установились **16 Python-дистрибутивов** и **156 npm-пакетов**; система применила все миграции, начальные справочники и bootstrap.
6. Проверены импорты Django/DRF/psycopg/openpyxl, настоящий начальный пароль setup, **11 сотрудников**, **4 способа выдачи**, **0 экспертиз**. Реальные и демо-экспертизы не создавались.
7. Django `check`, TypeScript и production-сборка фронтенда прошли. Esbuild работает с комплектным платформенным бинарным пакетом без lifecycle-загрузок.
8. Повторный `CheckOnly` после установки подтвердил неизменность исходных 18 файлов.
9. Отдельная тестовая PostgreSQL на **55433** остановлена; отсутствие слушателя проверено. Рабочая БД и веб-серверы не останавливались.

Совместимые Git/Python/Node на этой машине использовались повторно. Проверка не означает запуск EXE/MSI на отдельной чистой ОС или отключение сети всей машины: изолированный процесс работал с offline-флагами и недоступным прокси. Автономная ветка не вызывает загрузчик установщиков и не выполняет npm lifecycle-скрипты.

При первой упаковке плоского npm-кэша обнаружен путь длиной 265 символов, с которым не справился `Copy-Item` в Windows PowerShell. Кэш заменён одним `npm-cache.tgz`; внутри него сохраняется стандартная структура npm. Изначально файлы распаковывались через `tar.exe`; после сообщения владельца об отсутствующем `xz` эта зависимость заменена стандартными библиотеками Python. Текущая проверка исправления: [распаковка без внешних программ](offline-extractor-fix-2026-10-30.md).

Полный набор для установки — отдельный ZIP. В Git остаются код и скрипты; бинарные установщики и библиотечные кэши игнорируются. Google-импорт требует связи с Google, но без сети можно перенести журнал файлом XLSX.

Локальные логи: `.runtime/offline-preparation.log`, `.runtime/offline-missing-package.log`, `.runtime/offline-install-smoke.log`. Существующие тесты приложения не запускались повторно: бизнес-код и его зависимости не менялись, проверялся новый способ доставки тех же зафиксированных версий.
