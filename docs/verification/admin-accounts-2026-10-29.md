# Администрирование учёток — 29.10.2026

## Реализовано

- `/access`: отдельная кнопка добавления сотрудника по `employees.create`. Создание карточки по ФИО открывает существующие формы логина/пароля и назначения ролей. Не добавляет роли или квалификацию автоматически.
- `/people`: кнопка добавления доступна также из открытой карточки. Существующий ввод первоначального пароля не переделывался.
- `POST /api/v1/employees/{id}/account/reset-password/`: отдельное право `users.reset_password`, только `institution`; тело `{password, reason?}`, ответ `{id, username, is_active}`. Django-валидация и хеширование; атомарная запись только поля пароля; аудит без пароля и хеша. Не включает заблокированный вход и не меняет другие сведения.
- В персональном входе кнопка сброса и два ввода нового пароля. После успеха/отмены значения очищаются. Это непосредственная административная смена, не почтовый сброс и не обязательная смена при следующем входе.
- Обычная навигация/выход из системы не прерывает ожидающую ответа команду этих форм. Несохранённый черновик по-прежнему можно оставить после подтверждения.

## Независимое ревью и исправления

Свежий read-only reviewer проверил только этот срез, исключая ранее сделанное сворачивание напоминаний. Critical и Minor нет; два Important приняты и исправлены одним проходом:

1. Пропущенный `EmployeeOrganization.saving` в агрегате занятости карточки. Тест с ожидающим ответом кадрового назначения воспроизвёл уход в новую карточку; теперь кнопка отключена, контекст сохраняется.
2. Маршрутная защита учитывала только черновик, а не отправленную команду. Три параметризованных теста воспроизвели уход при сбросе/создании сотрудника/создании логина. В общий `useDirtyGuard` добавлена необязательная проверка занятости для этих родителей. Аналогичный тест выхода из системы также RED→GREEN.

Сохранены границы ревью: не менялись старые механизмы конкурентного создания логина, публичная регистрация, email и принудительная смена пароля не реализовывались. Новый механизм создания сотрудника по-прежнему использует существующий endpoint, а не обещает универсальную идемпотентность при потере сетевого ответа.

## Локальное применение

Перезапущен только Django на `127.0.0.1:8000`, существующий Vite PID134880 оставлен на `0.0.0.0:5173`.

Владелец отдельно разрешил добавить `users.reset_password` в персональную роль «Полный доступ · setup». Через штатный API ролей применено ровно это дополнение: версия3→4, существующие63 разрешения и области сохранены. Общие роли не менялись. В первой проверке различался порядок сериализованного списка; смысловое равенство подтверждено по before/after аудита и повторной order-insensitive проверкой. Доказательство без секретов: `.runtime/admin-accounts-grant-proof.json`.

В рабочей БД осталось12 сотрудников и480 экспертиз. Для браузерной проверки не создавались сотрудники и не сбрасывались реальные пароли. Проверена форма создания без отправки. При повторной загрузке обнаружена текущая браузерная сессия `loginov-dl`, не setup: отсутствие административных кнопок у неё соответствует её правам. Сессию владельца не переключали.

## Решения исполнителя

- Продолжена работа в текущем feature-checkout с существующим runtime, без новой копии приложения; соседние несохранённые изменения напоминаний сохраняются отдельно.
- Создание разделено на карточку и персональный вход: ошибка логина повторяется для того же человека; автоматической выдачи прав нет.
- Не добавлены email-приглашения, обязательная смена пароля и новые поля БД — это вне запроса.
- Общая защита получила только необязательный признак выполняющейся команды. Остальные вызовы сохраняют прежнее поведение; защищены также выход и кадровое назначение внутри той же карточки.

Изменения локальные, без push. Материальные данные не удалялись.
