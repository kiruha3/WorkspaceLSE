# Спецификация АИС ФГБУ Абаканская ЛСЭ на Django и Vue

Версия 0.1 · 27 октября 2026 года · проект для согласования перед реализацией.

Цель — полноценное рабочее место учреждения: от поступления постановления или определения до назначения, производства, переписки, результата, выдачи и отчётности из тех же данных. В новом самостоятельном репозитории находятся и Django backend, и Vue frontend. Существующие PHP-проекты, рабочие базы, Excel и Google Sheets не изменяются этой разработкой автоматически.

Главные решения владельца: Django; отдельный репозиторий внутри `E:/VLSE`; персональные учётные записи; назначаемые сотрудникам роли с настраиваемыми правами; совмещение руководящей и экспертной работы; несколько специальностей у сотрудника. Стажировка учитывается по конкретной специальности, но не позволяет назначать сотрудника на экспертизы по ней.

Техническая архитектура и порядок этапов ниже — предлагаемая реализация этих требований. Наличие спецификации не означает, что API или база уже созданы.

- `E:/VLSE/TECHNICAL_SPECIFICATION_WORKPLACES.md`, версия 0.6: назначение учреждения, данные, сценарии, импорт, документы и отчётность.

- `E:/VLSE/web-vue/docs/mockups/expertise-workflow-v1/prototype/index.html`: кликабельное предложение основного пути. Переключатель рабочих мест в нём — демонстрация, не механизм авторизации.

Не входят в первый выпуск: полный кадровый документооборот и расчёт зарплаты, автоматическая бухгалтерия/банковская оплата, юридически значимая ЭП, автоматическая отправка во внешние судебные системы, произвольные интеграции, многопользовательское редактирование текста заключения и разделы 7–8 отчётности без отдельного регистра. Сведения для этих расширений не следует прятать в универсальный JSON вместо предметной модели.

## 2. Архитектура и новый репозиторий

### 2.1 Рекомендуемая схема

Модульный Django-монолит с REST API и отдельным Vue SPA в одном репозитории. Одна база PostgreSQL; файлы отделены от строк учёта; в production у браузера один origin. Разделение на микросервисы не требуется для текущего учреждения: оно усложнило бы транзакции назначения, нумерации и выдачи. Серверные Django-шаблоны не выбраны основным интерфейсом, поскольку владелец уже выбрал Vue и имеются макеты.

```text
Браузер сотрудника
  └─ Vue 3 SPA
       └─ /api/v1 → Django + Django REST Framework
                       ├─ PostgreSQL: учёт, права, связи и история
                       ├─ закрытое файловое хранилище: оригиналы и версии
                       └─ задания импорта / подготовки отчётов и предпросмотра

Один origin: / — Vue, /api/ — Django, /admin/ — технический Django Admin
```

Все изменения бизнес-состояний выполняются через Django. Браузер не является источником прав, статусов готовности или окончательного расчёта отчёта. Django Admin нужен для сопровождения, но не заменяет рабочие места и не должен предоставлять обход обязательных бизнес-команд.

### 2.2 Технологии

| Слой | Выбор для проекта | Обоснование / граница |
|---|---|---|
| Backend | Python 3.13, Django 5.2 LTS, Django REST Framework | Предлагаемый поддерживаемый базис. Точные patch-версии фиксируются при создании окружения и проверяются совместно |
| База | PostgreSQL 17, psycopg 3 | Транзакции, ограничения уникальности, связи, индексы и блокировки |
| Frontend | Vue 3, TypeScript, Vite, Vue Router | Типизированные формы, независимые страницы, знакомая проекту технология |
| Общее состояние | Pinia для пользователя, прав, справочников и общих фильтров | Не складывать туда каждую локальную форму или все серверные записи |
| API | Версионированный REST, OpenAPI и генерируемые типы клиента | Один договор для фронта, тестов и будущих интеграций |
| Авторизация | Django session + CSRF, один origin | Для браузерного рабочего места; JWT и токены в localStorage не нужны по умолчанию |
| Файлы | Закрытый локальный volume в первом развёртывании; абстракция хранилища | Переход к объектному хранилищу не меняет бизнес-связи документов |
| Проверки | Django/pytest, PostgreSQL integration tests, Vue unit/component tests, браузерные E2E | SQLite не подменяет проверку конкурентных команд и ограничений PostgreSQL |
| Развёртывание | Docker Compose для dev/stage и воспроизводимый production-профиль | Не зависит от старой VM или PHP-БД; без запуска лишних worker-процессов |

Выбор Django 5.2 LTS предложен из-за срока поддержки до апреля 2028 года, а не как утверждение, что это самая новая ветка. [Политика и таблица поддерживаемых версий Django](https://www.djangoproject.com/download/). Требования DRF включают Django 5.2 и Python 3.13. [Официальные требования DRF](https://www.django-rest-framework.org/#requirements). Django 5.2 поддерживает PostgreSQL 14+, что допускает предложенную ветку 17. [Поддержка PostgreSQL в Django](https://docs.djangoproject.com/en/5.2/ref/databases/#postgresql-notes).

Не устанавливать Celery, Redis, отдельный поисковый сервер и множество фоновых служб заранее. Короткие операции выполняются синхронно; длительные имеют `Job`, статус и ограниченный worker. Механизм worker выбирается на этапе файлов/импорта по измерениям; состояние задания хранится устойчиво, а не только в памяти HTTP-запроса. Один исполнитель и ограниченная параллельность — исходная настройка для локального компьютера.

## 3. Пользователь, должности, роли и специальности

Подробная и основная спецификация доступа: [Роли и права](access-control.md). Она определяет матрицу действий, объединение ролей, области доступа и проверки API.

Стартовые сотрудники, подтверждённые должности, предзаполнение отделов/специальностей и требования к расширению всех справочников и таблиц: [Начальные данные и развитие таблиц](initial-data-and-tables.md). Власова Т.В. — начальник отдела 3; Колосова Ю.О. — начальник отдела 4; Миндибекова Т.М. — заместитель в отделе 3; Логинов Д.Л. — заместитель в отделе 4. Директор и делопроизводитель предусмотрены, персональные сведения пока не сообщены.

### 3.1 Разделение сущностей

| Сущность | Что означает | Что не заменяет |
|---|---|---|
| `User` | Персональный логин, пароль, активность учётной записи, сессии | Сотрудника и его должность |
| `Employee` | Постоянная идентичность человека, связь с учётной записью при наличии | Написание фамилии в Excel |
| `EmployeeOrgAssignment` | Работа в подразделении/должности с датами и основанием | Отдельный логин или право на все экспертизы отдела |
| `Role` | Настраиваемый набор поддерживаемых действий | Должность, специальность и допуск |
| `EmployeeRole` | Назначенная сотруднику роль, область и срок действия | Глобальное поле `user.role` с единственным значением |
| `EmployeeSpecialty` | Статус конкретной специальности у сотрудника и его история | Единый статус «стажёр» для всего человека |

У одного сотрудника может быть несколько должностей, ролей и специальностей. Например: начальник отдела 3; роли «Руководитель отдела» и «Эксперт»; полученная 18.1, полученная 19.1, обучение по 13.1. Он назначает в своей разрешённой области, а по собственным назначениям работает как эксперт: приостанавливает, возобновляет и завершает. По 13.1 его назначать нельзя до подтверждённого получения специальности.

Нельзя считать любое право руководителя разрешением приостанавливать чужие работы: для этого нужно отдельное право с областью. Владелец подтвердил экспертные действия начальника на его собственных назначениях; полномочия по чужим работам задаются отдельно в ролевой матрице.

### 3.2 Учётная запись

`accounts.User` создаётся как собственная модель на основе `AbstractUser` с первой миграции; `AUTH_USER_MODEL` указывается до создания миграций. Смена модели пользователя после наполнения не должна стать будущей отдельной миграцией проекта. [Рекомендации Django по собственной модели пользователя](https://docs.djangoproject.com/en/5.2/topics/auth/customizing/#using-a-custom-user-model-when-starting-a-project).

Для обычного сотрудника — одна активная учётная запись. Сотрудник без логина допустим: он нужен для истории и кадрового реестра. Увольнение/неактивность сотрудника, блокировка входа и прекращение конкретной роли — разные события с управляемыми последствиями. Прежние участия и документы не удаляются.

В первом выпуске: вход, выход, просмотр собственного профиля, смена своего пароля, административное создание учётной записи, временный пароль/обязательная смена, блокировка и завершение сессий. Саморегистрация не нужна. Восстановление через email не обещается до настройки почты; административный сброс имеет отдельное право.

### 3.3 Несколько специальностей и обучение

`EmployeeSpecialty` связывает сотрудника и экспертную специальность. Минимум:

- `employee_id`, `specialty_id` — устойчивые ссылки;
- статус `training` или `qualified`; `unknown_legacy` — техническое состояние неразобранного импорта, не допуск;
- известные даты начала обучения, получения специальности и окончания действия; отсутствие даты не превращается в вымышленный бессрочный допуск;
- документ-основание и подтверждающий файл при наличии;
- наставник при наличии, заметки, автор проверки и история переходов;
- прекращение/приостановление допуска — будущие отдельные события, а не стирание старой квалификации.

Подтверждено владельцем: `training` означает **только учёт обучения, без назначения на экспертизы по этой специальности**. Запрет действует на основного исполнителя, участника комиссии, замену и импорт новых назначений. Допуск по другой полученной специальности при этом не запрещается. Роли, включая роль руководителя, не обходят это правило.

Для назначения нужны соответствующая специальность со статусом «Получена», активные сотрудник/специальность и разрешённое действие назначающего. Последнее уточнение владельца28.10.2026: отдельное подтверждение, документ, основание и даты необязательны; даты хранятся для справки и не блокируют назначение. Исторические неизвестные сведения не превращаются автоматически в `qualified`. Исторические участия из старого журнала сохраняются с происхождением; это не создание нового назначения.

Полученную специальность можно внести сразу или явно отметить полученной существующую запись, с правом `specialties.qualify`, без обязательного основания/даты. Изменение справочных дат не меняет статус и не переписывает историю прежних назначений. Самообслуживание без этого права не позволяет указать себе полученную специальность. `training` по-прежнему означает только обучение, без назначения по этой специальности.

## 4. Предметная модель данных

У основных сущностей — стабильный UUID; отображаемые номера и ФИО не используются вместо ID. Ключевые поля имеют собственные типизированные колонки и ограничения. JSON применяется для неизменённой исходной строки импорта, снимка расчёта и дополнительных диагностических сведений, а не для скрытой реляционной схемы.

|---|---|
| `Institution` | Название ФГБУ Абаканская ЛСЭ, реквизиты после настройки; в первом выпуске одно учреждение |

## 5. Бизнес-инварианты

### 5.1 Регистрация и номера

1. Минимум нового поступления: постановление либо определение, фото или зарегистрированное наличие бумажного оригинала. Скан бумажного оригинала можно добавить позднее. Неизвестные реквизиты не выдумываются; минимальная таблица обязательности утверждается отдельно для каждого действия.
2. Поступление и материал могут существовать до номера экспертизы. До команды регистрации отображается предварительный номер.
3. Номер вводит и закрепляет делопроизводитель. Подсказка последнего номера не резервирует и не присваивает следующий. Область последовательности и переход года открыты; автоинкремент пока не реализуется.
4. Предлагаемое ограничение БД: уникальность нормализованного текущего полного номера в учреждении. Старый номер в скобках хранится отдельно, не участвует в распознавании категории текущей работы.
5. Проверка номера и запись выполняются атомарно; одновременная регистрация одинакового номера даёт один успех и один конфликт, не два дубля.
6. Конкретного эксперта назначает начальник отдела в своей разрешённой области. Первоначальный выбор отдела — открытое правило; до его решения отдел выбирается явно, без автоматического распределения.
7. Ошибочная регистрация исправляется отдельным действием с основанием и историей. Нельзя незаметно удалить номер, перепривязать выданный документ или перезаписать конфликтующую запись импорта.

### 5.2 Характер назначения и состав

`appointment_nature` — `primary | repeated | additional`, для старых неполных данных возможно отдельное неизвестное значение. Комиссионный состав и комплексная группа — независимые измерения. Повторная/дополнительная работа может быть комиссионной или комплексной.

Комиссия: одна экспертиза, один номер, несколько квалифицированных участников. Комплекс: отдельный номер по каждой специальности, участники связаны с соответствующей работой. Нельзя создавать номер только потому, что добавлен второй эксперт той же специальности.

Признаки можно задавать при регистрации и уточнять экспертом. Однако превращение в комплексную работу с новой специальностью требует самостоятельной регистрации нужного номера делопроизводителем. Для запроса эксперта сначала существует план/ожидающее изменение группы; отсутствующий номер не выдумывается. Изменение состава комиссии требует нового назначения участников начальником отдела. Уже сохранённые назначения не переписываются скрытым флажком.

Перепоручение сохраняет номер и историю: прежнее назначение завершается, новое начинается атомарно. В текущем списке сотрудника работа учитывается у получателя; бывший исполнитель виден в истории. Однофамильцы и варианты падежа не создают новых сотрудников без проверки.

### 5.3 Состояния, сроки и даты

Канонические состояния: `in_progress`, `suspended`, `completed`, `without_execution`. Исходные «Возврат без исполнения», «Завершена без исполнения», «Без исполнения» нормализуются в одно состояние; обычная «Завершена» — отдельно.

- Поступление, завершение/решение без исполнения, отправка письма, физическая выдача и доставка — самостоятельные даты и события.
- Начальник, назначенный экспертом, выполняет экспертные действия на своих работах. Нужное действие и область проверяются, а не запрещаются названием должности.
- Приостановка и возобновление выполняются экспертом либо делопроизводителем с соответствующим правом и основанием. У каждой экспертизы свой интервал; одна приостановка не останавливает всю комплексную группу.
- Запрошенный срок не считается согласованным. После получения согласования сохраняются исходный срок, новый срок и подтверждающий документ.
- Пустая дата выдачи означает отсутствие подтверждённой выдачи. Например, 358/4-5-26 не забрали — это допустимое состояние ожидания, а не повод выдумать дату.
- Решение вернуть материал имеет свою дату `return_decision_at`; фактический возврат/выдача — `issued_at` и движение материалов. Legacy-поле `returnedAt` сопоставляется по его действительному смыслу, не переименовывается вслепую.
- Календарные дни, рабочие дни и срок с исключением приостановок — разные показатели. Метод и дата расчёта всегда видимы. В предварительной выборке календарные дни включают обе границы; юридический срок этим не подменяется.

### 5.4 Результат и комплект выдачи

Эксперт завершает работу и подкрепляет подготовленный документ. Новый этап согласования начальником и юридически значимая ЭП не вводятся. Полный СНДЗ — сообщение о невозможности дать заключение; отдельный нерешённый вопрос в обычном заключении не превращает весь итог в СНДЗ. Решение «без исполнения» не является разновидностью заключения.

Для структурированных Q/R/S/T: неотрицательные целые значения; при подтверждённой полноте `Q = R + S + T`. Неизвестное — `null`, а не ноль. Строка вида `1 СНДЗ` в T может означать один нерешённый вопрос с пояснением; исходный текст сохраняется. Полные причины СНДЗ и причины отдельных нерешённых вопросов — разные справочники и связи. Вариант применения нескольких причин требует отдельного согласования; неизвестное не считается «иные причины».

| Комплект | Подтверждённое правило |
|---|---|
| Базовый | Итоговый документ, материалы дела, подписка эксперта, сопроводительное письмо |
| Категория 1 — уголовное, 5 — КУСП | Дополнительно уведомление |
| Категория 2 — гражданское, 3 — арбитражное | Дополнительно выписать счёт |
| Категория 4 — КоАП, обычное заключение | Материалы дела, подписка эксперта, сопроводительное письмо, заключение эксперта; уточнение владельца 28.10.2026 |
| Категория 6 — исследование по заявлению | Материалы, подписка эксперта, сопроводительное письмо, акт экспертного исследования; уточнение владельца 28.10.2026 |
| Платная работа, в том числе акт экспертного исследования | Дополнительно счёт; уточнение владельца 28.10.2026. Платность — явно записанный факт, не вывод из категории или суммы. Ранее утверждённое требование счёта для категорий 2/3 этим не отменяется |
| Полный СНДЗ, возврат, комплект подписок комиссии | Специальный состав пока требует подтверждения; не выбирать молча шаблон обычного заключения |

Платность фиксируется уполномоченным делопроизводителем отдельно по каждой работе в редакции комплекта выдачи. Пока она неизвестна, можно сохранить черновик, но нельзя подтвердить проверку и фактическую выдачу. Значение не выводится из суммы журнала или категории. Изменение платности создаёт новую редакцию и требует повторной проверки комплекта. Старые сведения не заполняются массово и не меняются задним числом.

Делопроизводитель проверяет комплект и фиксирует фактическую выдачу. Счёт, его отправка, сумма и оплата — самостоятельные факты; предварительная оплата не установлена как обязательное условие выдачи. Автоматическое формирование счёта требует утверждённого шаблона и реквизитов.

Частичная выдача при другой продолжающейся работе по тем же материалам не утверждена. До решения первая версия показывает оставшиеся работы и разрешает только подтверждённый полный комплект; не объявляет весь материал выданным после завершения одного номера. Число подписок при комиссии также не выводится автоматически из числа участников без согласованного шаблона.

Выдача — атомарная команда с повторной проверкой завершённости, комплекта и прав. Повтор нажатия/запроса не создаёт вторую выдачу.

## 6. Документы и корреспонденция

### 6.1 Файлы и просмотр

Реализация среза28.10.2026: отдельный архив `/expertises/:id/documents` на Document/FileVersion и WorkDocumentLink, общий файл с несколькими дополнительными связями, мягкое снятие одной связи, агрегированные процессные источники и явный выбор принятой версии. Права documents.link/unlink настраиваются отдельно, не выдаются автоматически. External_link хранит только URL до явного сохранения копии; выбранная браузером папка загружается последовательно с относительными путями как метаданными. Контракт: `docs/api-documents.md`. Применение к рабочей БД фиксируется отдельно в проверке; последующие абзацы сохраняют целевые требования, а не объявляют весь файловый модуль завершённым.

Пользователь добавляет файл, регистрирует URL либо выбирает доступную подключённую папку. Локальный выбор папки — разовая загрузка выбранных файлов, не постоянный доступ сервера к компьютеру. Текстовый путь `C:\...` ничего не подключает.

У источника явно различаются сохранённая копия и ссылка. У документа — реквизиты, вид, исходное имя файла, происхождение, автор/дата добавления и связи с несколькими объектами. Один файл не копируется на каждую экспертизу комплексной группы. Отвязка от одного объекта не удаляет прочие связи.

PDF и изображения просматриваются внутри веба. Для офисных форматов — согласованное производное представление после конвертации; оригинал хранится отдельно. Необработанный формат, недоступная ссылка, неподдерживаемый предпросмотр и отсутствующий оригинал показываются различимо. Наличие текста описи не доказывает наличие загруженного документа.

Замена скана того же основания создаёт новую версию. Дополнительное или заменяющее определение — новый документ с собственными реквизитами и связью `supplements | replaces`, не новая версия старого PDF. Обновление копии из папки/URL принимается явно и сохраняет прежнюю версию. Замена общего файла показывает затрагиваемые связи.

Управляемые папки и внешние URL подключаются через серверный адаптер, не прямыми сетевыми ключами в Vue. Внешний источник может запрещать встраивание: тогда показывается доступное действие без обещания просмотра любого URL. Политика прав распространяется на содержимое, предпросмотр, оригинал и список связей одинаково.

### 6.2 Письма и контроль

Поддерживаются входящие и исходящие запросы, ответы, информационные письма и переписка с судами. Письмо может относиться к одной/нескольким экспертизам, материалу или быть самостоятельным. Внешний номер документа, внутренний входящий/исходящий номер и номер экспертизы не смешиваются.

Черновик → регистрация → фиксация отправки — независимые действия. Получение/доставка и снятие с контроля — отдельные факты. Создание письма в вебе не отправляет его во внешнюю систему в первом выпуске.

Ответ связывается с исходным запросом; допустимы несколько частичных ответов и дополнительное поступление файлов. Частичный ответ не закрывает контроль автоматически. Информационное письмо не требует ответа только из-за выбранного вида: требование задаётся отдельно.

Эксперт/делопроизводитель с соответствующим правом фиксирует решение по контролю. Завершение экспертизы не снимает письма с контроля; незакрытые запросы видны отдельным списком. Окончательный регламент завершения таких запросов остаётся открытым.

Для периода пользователь явно выбирает дату поступления, завершения либо фактической выдачи. Последняя дата не извлекается из произвольного текста без правила и происхождения.

### 7.2 Отчётность

Backend рассчитывает 15.1 по утверждённой версии бланка и правил; Vue отображает результат и расшифровку. Существующие TypeScript-расчёты и тесты используются как материал для контрольных примеров, а не как безусловное требование повторить каждую старую ошибку. Сравнение Python/TypeScript проводится на одних фиксированных входах с протоколом расхождений и решениями.

У каждого запуска: период, редакция бланка, версия правил, снимок фактов/полноты, инициатор, область доступа, замечания и итоговый файл. Каждая ячейка имеет объяснение и участвующие регистрации. Повторная выгрузка воспроизводима; изменение исходной записи не меняет уже сохранённый снимок молча.

| Раздел | Что нужно проверить и покрыть |
|---|---|
| 1 | Поступление, завершение, СНДЗ и его причины, категории, исследования, начало/конец производства; полнота журнала подтверждается отдельно |
| 2 | Вопросы, виды выводов и количество нерешённых по причинам; правило включения исследований ещё утверждается |
| 3 | Длительность и известные причины; исходный/согласованный срок и приостановки не смешиваются |
| 4 | Сложность, возвраты и соответствующие дополнительные признаки по конкретному бланку |
| 5 | Органы назначения и иные признаки по бланку; не подменять тип органа категорией дела |
| 6 | Факт госзадания по категориям 1/5, общий план 294 на 2026, отдельная неизвестная разбивка по специальностям |

Заголовки таблицы — маршрутизация работ по текущему образцу, не новая нормативная формулировка формы. Шаблон `10004_151_2609.xlsx` и его местная подготовленная копия должны иметь зафиксированную версию и проверенную структуру; актуальность бланка утверждает владелец.

Единица подсчёта указывается явно: регистрация, материал, участие, комплексная группа или документ. По уточнению владельца фактические Q/R/S/T каждой зарегистрированной работы учитываются отдельно, даже при одинаковом тексте общей описи. Число участий комиссии нельзя складывать как число уникальных экспертиз учреждения.

Неизвестное не превращается в ноль. Отсутствие одного факта не исключает целую запись из всех известных показателей. Допускается частичная XLSX-выгрузка с пустыми затронутыми ячейками и протоколом замечаний. Готовность полного отчёта требует отдельно согласованных данных и правил, а не просто созданной БД.

Общий годовой план 294 не делится автоматически по месяцам и специальностям. Переходящие из прежней организации номера в скобках не являются доказательством остатков на 1 января новой организации.

| Письма | `/letters/`, `/{id}/register/`, `/{id}/mark-sent/`, `/{id}/replies/`, связи и файлы |
| Контроль | `/control-tasks/`, `/{id}/close/`, отдельные ответственные и основания |
| Выдача | `/materials/{id}/issue-packages/`, `/issue-packages/{id}/readiness/`, `/{id}/issue/` |
| Импорт | `/imports/preview/`, `/{id}/rows/`, `/{id}/apply/`, `/imports/{id}/result/` |
| Выгрузки | `/expertises/export/`, `/reports/form-151/runs/`, `/report-runs/{id}/gaps/`, `/cells/`, `/download/` |
| История / задания | Доступная история объекта; `/jobs/{id}/` для длительных операций без раскрытия чужих результатов |

Пути — договор проектирования; к началу соответствующего этапа оформляются в OpenAPI с request/response-примерами. Не требуется заранее генерировать десятки пустых CRUD-viewsets. Команда «завершить» не заменяется общим `PATCH status=completed`; назначение — не произвольным редактированием ID сотрудника.

### 8.2 Общие контракты

- Списки: `{count, next, previous, results}`, стабильная сортировка с ID вторым ключом, разрешённые фильтры и ограничение размера страницы. Итоги считаются по всему разрешённому queryset.
- Команды: версия объекта (`expected_version` или `If-Match`) и ключ повторного запроса для регистрации, выдачи, импорта и формирования отчёта. Один ключ с другим содержимым — конфликт.
- Успешная запись возвращает сохранённое состояние и новую версию. Устаревшее редактирование — 409 с информацией для обновления, не тихая перезапись.
- Ошибка: `code`, `message`, `field_errors`, `request_id`, при необходимости `details`. Во фронте различаются неверные поля, конфликт, отсутствие доступа и сбой операции.
- Проектный контракт: 401 `auth_required`, 403 `permission_denied`, 404 недоступный/несуществующий объект по принятой политике, 409 конфликт, 400 валидация. У SessionAuthentication DRF возможен 403 без сессии; нужный проекту 401 должен быть реализован и проверен адаптером, не предполагается встроенным поведением.
- Версия документа, назначения и материального движения сохраняется атомарно с бизнес-командой и AuditEvent. Кэш/уведомления запускаются после успешного commit.
- Сервер возвращает допустимые действия/причины недоступности для карточки; фронт не вычисляет полномочия по названию должности. При прямом запросе сервер всё равно проверяет права.

Пример отказа назначения стажёра:

```json
{
  "code": "specialty_not_qualified",
  "message": "По выбранной специальности сотрудник пока обучается и не может быть назначен на экспертизу.",
  "field_errors": {"employee_id": ["Статус специальности: training"]}
}
```

SessionAuthentication подходит клиентам в общем сессионном контексте; изменяющим запросам необходим CSRF, а login должен проверять CSRF и до аутентификации. Это часть базового договора входа, не отдельный аудит. [Официальная документация DRF](https://www.django-rest-framework.org/api-guide/authentication/#sessionauthentication).

Карточка сотрудника имеет вкладки «Общее», «Должности и подразделения», «Специальности», «Обучение», «Назначения», «Роли и доступ» по правам, «История». Таблицы показывают квалификацию по каждой специальности. Начальник-эксперт использует один профиль; переключение представления «руководство/мои экспертизы» меняет удобство просмотра, не полномочия сессии.

Внешний вид: полноширинный рабочий стол, палитра существующего проекта на основе minjust-expert24.ru, точное название учреждения, единые таблицы/поля/диалоги. Загрузка, пустая выборка, неизвестные данные, ошибка файла, сетевой сбой, несохранённая форма и конфликт версий имеют различимые состояния. Нельзя показывать «сохранено», пока сервер не подтвердил запись. Введённое сохраняется при ошибке; перед уходом с несохранённой формы есть подтверждение.

Реестр пригоден для 1920/1440/1280 px без узкого iframe; на планшете панели перестраиваются, на телефоне сохраняются основные действия и читабельные реквизиты. Большие таблицы допускают горизонтальную прокрутку, но не всего приложения. Клавиатура, видимый focus, подписи полей и текст ошибок обязательны. Неподдерживаемый файл не изображается пустым просмотрщиком.

## 10. Перенос данных и самостоятельность новой системы

Новая база создаётся отдельно. Старая VM не нужна для нового окружения, если доступны подтверждённые исходники, схемы, бэкапы и снимки данных; для невыясненного legacy-поведения она может понадобиться как источник проверки. Это не разрешение удалять старую систему.

Порядок импорта:

1. Прочитать только согласованный первый лист или настроенный Google-источник без записи обратно.
2. Сохранить исходную строку, сведения об источнике/листе/версии, устойчивое сопоставление и протокол нормализации.
3. Показать новые, изменённые, неизменённые и ошибочные строки. Совпадение текста описи и фамилии не является ключом личности/экспертизы.
4. Вручную подтвердить неоднозначных сотрудников, исторические номера, даты, квалификации и связи. Не создавать `qualified` по упоминанию фамилии в старом журнале.
5. Применить подтверждённый пакет атомарно; повторный импорт не создаёт дублей. Повторное обновление не стирает серверные исправления без предпросмотра конфликта.
6. Сверить количество регистраций, исходные значения, выборки и отчётные показатели. Откат конкретного импорта не должен отменять чужие последующие изменения: для конфликтов нужен отдельный протокол.

Строка Excel и номер строки — происхождение, не вечный системный ID: строки могут перемещаться. Для Google предпочтителен согласованный стабильный идентификатор записи либо явная таблица сопоставления. Способ устойчивого сопоставления при исправлении самого номера утверждается до автоматической синхронизации.

Локальные 466 строк макета — старый снимок, не доказательство актуальности после исправлений Google. Реальные данные не превращаются в публичные seed-файлы. Для воспроизводимых проверок используются искусственные кейсы; полный импорт идёт в разрешённую локальную/тестовую базу.

## 11. Этапы реализации и проверка готовности

У каждого этапа — новая работающая вертикаль: backend, API, фронт и тесты, а не месяцы невидимой подготовки. Прежде чем начать продуктовый код, согласовать эту спецификацию и открытые правила, относящиеся к ближайшему этапу.

| Этап | Что создаём | Где изменяем | Проверяемый результат |
|---|---|---|---|
| 0 | Утверждение схемы данных, доступа, словаря и первого среза | `docs/`, начальные API-примеры | Нет скрытых взаимоисключающих ролей или статуса стажёра на всего сотрудника; открытые правила видны |
| 1 | Новый Git-репозиторий, Django/Vue окружение, User, login/logout, роли и их редактор | `backend/accounts`, `frontend/app`, `/login`, `/settings`, `infra` | Уже виден новый фронт: пользователь входит и получает реальные серверные права; два аккаунта не видят лишнее |
| 2 | Сотрудники, должности, несколько специальностей, обучение и справочники | `personnel`, `references`, `/people` | Один человек — несколько специальностей; trainee не назначается по обучаемой специальности, начальник совмещает экспертную роль |
| 3 | Приёмка → ручной номер → назначение → рабочая карточка | `intake`, `expertises`, соответствующие страницы | Первую экспертизу можно оформить и повторно открыть из БД; конкурирующие одинаковые номера не создают дубль |
| 4 | Файлы, основания, версии, письма, контроль, сроки | `documents`, `correspondence`, `expertises` | Подкреплённый PDF открывается внутри веба, запрос/частичный ответ/контроль имеют отдельные события |
| 5 | Результат и полный комплект выдачи для согласованных категорий | `expertises`, `intake`, документы и страницы результата/выдачи | Эксперт завершает, делопроизводитель выдаёт; по 1/5 уведомление, по 2/3 счёт; нет вымышленной даты получения |
| 6 | Импорт реального журнала и Python-расчёт 15.1 разделов 1–6 | `imports`, `reports`, `/reports` | Протокол сверки, расшифровка каждой ячейки, частичный экспорт; полный только при данных и утверждённых правилах |
| 7 | Приёмка рабочих мест, исправления, резервирование и развёртывание | E2E, frontend, infra, эксплуатационные инструкции | Полный согласованный путь воспроизводится с разных учётных записей; восстановление новой БД/файлов проверено |

На первом этапе визуально доступны вход, персональная оболочка и управление ролями; после третьего — рабочая экспертиза в собственной БД. Старый frontend не удаляется до приёмки соответствующего нового модуля. Перенос доменных расчётов и дизайна не означает копирование монолитного компонента целиком.

## 12. Открытые решения и критерий завершения

Не блокируют описание архитектуры, но до соответствующей функции требуют решения:

1. Кто первоначально определяет отдел; область нумерации и её переход года.
2. Полные названия отделов 3/4, ФИО директора и делопроизводителя, назначенный администратор доступа. Начальники и заместители уже подтверждены в документе начальных данных.
3. Оформление прекращения/приостановления статуса полученной специальности остаётся отдельной процедурой. Последнее правило владельца28.10.2026: обязательного отдельного подтверждения нет; основание/документ и даты необязательны, даты справочные и не блокируют назначения; обучение/неуточнённые исторические сведения назначения не допускают.
4. Применение ролей «делопроизводитель», «кадровик», «руководитель учреждения» к чужим/межотдельским данным; начальная матрица в отдельном документе является предложением.
5. Специальные пакеты выдачи 4/6, СНДЗ и возврата, подписки комиссии, шаблоны счёта и уведомления; частичная выдача.
6. Регламент незавершённой переписки при окончании и исправления уже выданного результата.
7. Несколько причин полного СНДЗ/нераспределённых вопросов, исследования в разделе 2, 3214-р, полнота остатков, план по специальностям.
8. Утверждённая редакция бланка 15.1, финальный отчёт для сверки и стабильный ключ синхронизации Google.
9. Место развёртывания, объём и место файлового хранилища, утверждённые реквизиты/шаблоны документов.

Первая полноценная версия готова, когда согласованный набор рабочих сценариев выполняется на собственной БД и файлах с персональными аккаунтами и настраиваемыми ролями, воспроизводится после перезагрузки, проверен контрольными данными и принят владельцем. Один красивый экран, скрытые кнопки, число созданных endpoints или заполненная тестовая БД не заменяют этот критерий.
