# Роли и права АИС ФГБУ Абаканская ЛСЭ

Версия 0.1 · 27 октября 2026 года · часть [спецификации системы](specification.md).

Подтверждённое направление: сотрудникам назначаются роли, а действия роли настраиваются в правах. У сотрудника может быть несколько ролей. Должность, учётная запись, роль и экспертная специальность — разные сущности. Начальник отдела может одновременно выполнять экспертизы и приостанавливать собственную работу как назначенный эксперт. Стажировка по специальности не допускает назначения на экспертизы по ней.

Начальная матрица ниже — предложение для согласования. Она не выдаёт всем руководителям или делопроизводителям новые полномочия автоматически.

## 1. Принцип доступа

Для конкретного действия сервер проверяет одновременно:

1. Активную сессию и учётную запись, связанную с сотрудником.
2. Действующие назначения ролей сотрудника и сроки/область каждого назначения.
3. Наличие нужного действия в хотя бы одной из этих ролей.
4. Попадание объекта в область именно этого действия: свои, назначенные отделы, учреждение.
5. Предметные условия: квалификация по специальности, состояние работы, версия объекта, комплектность, обязательные даты/основания.

Условно:

```text
разрешено = активный пользователь
            И существует роль с нужным действием и подходящей областью
            И выполнены предметные условия операции
```

Две роли объединяют разрешения, но не отменяют ограничения предметной модели. Роль с просмотром учреждения не расширяет чужое право редактирования своего отдела. Право «назначить эксперта» не даёт права выдавать результат; роль руководителя не превращает обучение в полученную специальность.

В первой версии действует модель «разрешено явно»: без подходящего разрешения действие недоступно. Явные запрещающие роли и сложное наследование ролей не вводятся. Неотмеченный флажок в одной роли не отменяет разрешение другой — редактор показывает итог, чтобы это не было неожиданностью. Блокировка аккаунта и предметный запрет стажёра действуют независимо от объединения ролей.

## 2. Сущности и области

| Сущность | Минимальные данные |
|---|---|
| `User` | ID, уникальный логин, пароль Django, `is_active`, связь с сотрудником, служебные признаки и сессии |
| `Employee` | Постоянный ID человека; сотрудник может существовать без учётной записи |
| `Position` | Должность; начальник отдела — здесь, а не единственное значение поля роли пользователя |
| `PermissionDefinition` | Поддерживаемый код действия, модуль, подпись, допустимые области; определяется кодом сервера |
| `Role` | ID, название, описание, активность, версия; пользовательское название не участвует в проверке доступа |
| `RolePermission` | Роль, код действия, область действия; уникальная настройка поддерживаемого действия роли |
| `EmployeeRole` | Сотрудник, роль, выбранные подразделения/ограничение области, даты действия, основание, кто назначил |
| `EmployeeSpecialty` | Конкретная специальность, `training/qualified/unknown_legacy`, известные даты/основания и история |

Для `Role` можно использовать Django permissions как каталог поддерживаемых действий, но не вести две конкурирующие авторизации в `Group` и собственных ролях. Конкретная ORM-реализация выбирается одна; действия предметных команд регистрируются как custom permissions.

Должность помогает предложить начальный набор ролей, но не выдаёт права скрыто. Владелец/уполномоченный администратор явно назначает роль сотруднику. Изменение кадровой должности не должно незаметно удалить или расширить доступ без показанных последствий. Временное замещение оформляется назначением роли с областью/сроком, не вторым логином начальника.

Начальный регламент назначения экспертов: такое действие предоставляется начальнику отдела. Само название должности не заменяет назначение роли. Порядок замещения и выдачи этого права другим должностям должен быть утверждён, а не зашит сравнением текстовых названий.

### 2.1 Области

| Код | Значение | Применение |
|---|---|---|
| `own` | Текущие назначения пользователя либо порученная ему переписка | Результат, приостановка, свои файлы; история прежних назначений — отдельное чтение |
| `departments` | Явно выбранные отделы назначения роли | Руководство отделом; пустой набор не означает все отделы |
| `institution` | Учреждение | Разрешённый общий журнал, отчётность и администрирование |

У каждого действия каталог определяет допустимые области. Например, управление определением ролей в первом выпуске только `institution`, а редактирование своего профиля — `own`. Редактор не предлагает невозможные сочетания.

Дополнительное ограничение назначения роли может сузить область, но не расширить её. Итоговые объекты для действия — объединение областей разрешающих ролей, каждая после своего ограничения. Области не складываются отдельно от действий. Выбранные отделы хранятся по ID, не по цифрам в старых номерах.

В собственных работах учитывается текущее назначение. После передачи старая работа пропадает из текущей нагрузки прежнего исполнителя; право просмотра собственного исторического участия описывается отдельно. Для комиссии «своя работа» — работа с действующим участием сотрудника; стажёр не может стать таким участником по обучаемой специальности.

## 3. Начальные роли и совмещение

Названия — стартовые шаблоны, а не жёстко заданные режимы программы. Допускаются собственные роли учреждения и изменение их прав уполномоченным администратором.

| Роль | Стартовое назначение | Исходная область |
|---|---|---|
| Эксперт | Просмотр и производство своих назначений, документы, черновики писем, вопросы/результат, пауза/возобновление | Свои |
| Делопроизводитель | Приёмка, регистрация, номера, документы, журналы переписки, фиксация отправки и выдачи | Предлагается учреждение; точная область утверждается |
| Руководитель отдела | Обзор отдела, назначение и перепоручение квалифицированных исполнителей, контроль нагрузки | Назначенные отделы |
| Заместитель начальника отдела | Настраиваемый набор делегированных действий; не автоматическая копия полномочий начальника | Выбранный отдел и срок при наличии |
| Кадровый учёт | Сотрудники, должности, полученные специальности и обучение, подтверждение переходов | Предлагается учреждение; без автоматического доступа к текстам дел |
| Руководитель учреждения | Обзор разрешённых подразделений, показатели и отчётность | Учреждение; полномочия изменения отдельно |
| Администратор доступа | Пользователи, определение ролей, назначение, проверка и прекращение доступа | Учреждение |

Подтверждённый состав: Власова Т.В. — начальник отдела 3, Колосова Ю.О. — начальник отдела 4, Миндибекова Т.М. — заместитель в отделе 3, Логинов Д.Л. — заместитель в отделе 4. Должности остальных названных в журнале сотрудников — эксперты по уточнению владельца. Предзаполнение и основания: [Начальные сотрудники](initial-data-and-tables.md). Конкретные права заместителя на назначение, перепоручение и чужие работы ещё задаются владельцем через роль, а не выводятся из номера его экспертизы.

Примеры:

- Начальник отдела 3 получает «Руководитель отдела» в отделе 3 и «Эксперт» по своим работам. Два назначения ролей не требуют двух аккаунтов.
- Допустимо создать одну комбинированную роль с теми же правами. Проверка идёт по действиям и области, а не по количеству или названию ролей.
- Сотрудник, совмещающий делопроизводство и экспертную работу, получает обе роли; право завершать распространяется на его назначения, а право выдавать — на согласованную область делопроизводства.
- Кадровик может учитывать обучение по 13.1, не имея доступа к заключениям или права назначения на работы.
- Администратор доступа не обязан быть экспертом, кадровиком или владельцем содержимого всех дел. `manage_roles` само по себе не даёт `expertise.view`.

`is_staff` Django означает доступ к техническому Django Admin, а не должность «сотрудник учреждения». `is_superuser` — исключительный технический доступ, не обычная роль из рабочего редактора. Обычное управление ролями не предоставляет изменение этих флагов. Даже техническая операция не должна обходить ограничения данных через необработанный CRUD: стажёр не становится квалифицированным исполнителем только из-за привилегий инициатора.

## 4. Каталог действий

Коды — проектный контракт. Названия показываются по-русски. Новый код появляется вместе с обработчиком, областью, тестами и обновлением контракта; администратор не создаёт произвольное серверное действие текстовым полем.

| Модуль | Действия | Допустимые области / ограничения |
|---|---|---|
| Профиль | `profile.view`, `profile.change_password` | Свои |
| Учётные записи | `users.view`, `users.create`, `users.update`, `users.deactivate`, `users.reset_password`, `users.revoke_sessions` | Учреждение, по отдельным разрешениям |
| Роли | `access.roles.view`, `access.roles.manage`, `access.roles.assign`, `access.effective.view` | Учреждение в первом выпуске; нельзя смешать назначение готовой роли с редактированием её прав |
| Сотрудники | `employees.view`, `employees.create`, `employees.update`, `employees.deactivate` | Отделы/учреждение; основные рабочие сведения отдельно от закрытых кадровых данных |
| Кадровые назначения | `employees.org_assignments.manage`, `employees.history.view` | Отделы/учреждение по регламенту |
| Специальности | `specialties.view`, `specialties.training.manage`, `specialties.qualify`, `specialties.qualification.correct` | Кадровая область; самообслуживание не позволяет выдать себе допуск |
| Справочники | `references.view`, `references.manage` | Чтение нужных списков для своих форм; изменение по согласованной области |
| Приёмка | `receipts.view`, `receipts.create`, `receipts.register`, `receipts.amend` | Отделы/учреждение |
| Материалы | `materials.view`, `materials.create`, `materials.update`, `materials.movements.manage` | Свои/отделы/учреждение в зависимости от операции |
| Регистрация экспертизы | `expertise.view`, `expertise.register`, `expertise.registration.correct` | Номер закрепляет делопроизводитель; исправление отдельно от новой регистрации |
| Назначения | `expertise.assign`, `expertise.reassign`, `expertise.commission.manage` | Отделы/учреждение по регламенту; квалификация обязательна |
| Классификация | `expertise.classification.update`, `expertise.complex.plan` | Свои/отделы/учреждение; новый номер требует отдельной регистрации |
| Производство | `expertise.work.update`, `expertise.suspend`, `expertise.resume`, `expertise.deadline.record` | Свои/отделы/учреждение по явно заданному действию |
| Результат | `expertise.result.draft`, `expertise.complete`, `expertise.return_without_execution`, `expertise.closed.correct` | Свои по стартовому шаблону эксперта; расширение отдельно, закрытая корректировка требует основания |
| Нагрузка / история | `expertise.history.view`, `expertise.own_history.view`, `expertise.summary.view` | Свои/отделы/учреждение; текущее и историческое участие различаются |
| Документы | `documents.view`, `documents.upload`, `documents.link`, `documents.version.add`, `documents.unlink`, `documents.download` | По разрешённым связанным объектам; право на URL не заменяет право на содержимое |
| Письма | `letters.view`, `letters.draft`, `letters.register`, `letters.mark_sent`, `letters.reply` | Свои/отделы/учреждение; регистрация и отправка независимы |
| Контроль | `control.view`, `control.assign`, `control.close` | Свои/отделы/учреждение; право снять с контроля отдельно от создания ответа |
| Выдача | `issue.prepare`, `issue.check`, `issue.confirm` | Отделы/учреждение по стартовому регламенту делопроизводства |
| Выгрузки | `expertise.export`, `letters.export`, `reports.form151.view`, `reports.form151.run`, `reports.form151.download` | Каждое действие со своей областью; экспорт не шире разрешённого чтения |
| Планы / правила отчёта | `reports.plans.manage`, `reports.coverage.confirm` | Учреждение; ввод плана и подтверждение полноты — не обычная выгрузка |
| Импорт | `imports.preview`, `imports.apply`, `imports.results.view` | Утверждённая область; создание новых назначений всё равно проверяет квалификацию |
| Источники / сопровождение | `sources.manage`, `jobs.view`, `audit.view` | Отдельно от работы с делами; задания и история тоже фильтруются по доступу |

Чтение внутри карточки не равно полному кадровому доступу. Для минимального справочника выбора исполнителя доступен ID, отображаемое имя и пригодность по специальности/области, а не все сведения сотрудника и его права.

## 5. Предлагаемая исходная матрица

Обозначения: С — свои назначения/поручения, О — назначенные отделы, У — учреждение, — нет по умолчанию. Это шаблон для обсуждения, не уже действующие права. Разделение кадрового администратора и администратора доступа сохраняется.

| Действие | Эксперт | Делопроизводитель | Руководитель отдела | Кадровый учёт | Руководитель учреждения | Администратор доступа |
|---|---|---|---|---|---|---|
| Просмотр экспертиз | С | У | О | — | У | — |
| Приёмка / ручной номер | — | У | — | — | — | — |
| Назначение / перепоручение | — | — | О | — | Только отдельное разрешение | — |
| Правка своих рабочих данных | С | Только учётные поля по праву | С при экспертном назначении и соответствующей роли | — | Только при соответствующей роли/назначении | — |
| Приостановить / возобновить | С | У, требуется утверждение области | С при экспертной роли; чужие О только отдельным разрешением | — | Только отдельное разрешение | — |
| Завершить / итоговый документ | С | — | С при экспертной роли | — | Только при соответствующей роли/назначении | — |
| Исправить закрытую работу | — | — | — | — | — | — |
| Документы разрешённых работ | С | У | О | Только разрешённые кадровые документы | У по разрешению | — |
| Создать черновик письма | С | У | О по разрешению | По отдельному поручению | По разрешению | — |
| Зарегистрировать / зафиксировать отправку | — | У | — | — | — | — |
| Снять запрос с контроля | С | У, область утверждается | О только отдельно | — | Только отдельно | — |
| Проверить / выдать комплект | — | У | — | — | — | — |
| Кадровые сведения / специальности | Рабочий минимум | Рабочий минимум | Рабочий минимум О | У | Разрешённый обзор | Не автоматически |
| Роли и учётные записи | Свой профиль | Свой профиль | Свой профиль | Свой профиль | Свой профиль | У |
| Отчёт / выгрузка | С по нужным формам | У по разрешённым журналам | О | Кадровая выборка | У | Не автоматически |

Корректировка закрытого результата по умолчанию не выдана никому из обычных шаблонов; владелец определяет ответственных, а администратор добавляет конкретной роли `expertise.closed.correct` с областью. Это не назначение такого бизнес-права техническому superuser по умолчанию.

## 6. Проверки, которые роль не обходит

Уточнение владельца от 28.10.2026: подтверждённую полученную специальность допускается использовать без известной даты получения после явного действия ответственного сотрудника с непустым основанием. Дата остаётся `null`, а не выдумывается. `training` и `unknown_legacy` по-прежнему не дают допуска; известный истёкший срок учитывается независимо от отсутствия даты получения.

| Операция | Дополнительная обязательная проверка |
|---|---|
| Назначить / заменить / добавить в комиссию | Сотрудник активен; именно эта специальность получена; не `training`; известное ограничение срока учитывается |
| Начальник выполняет свою экспертизу | Есть квалификация и действующее экспертное назначение; экспертные действия разрешены его ролью |
| Приостановить / возобновить | Допустимое состояние, корректная дата, основание и версия; отдельная работа, не вся группа |
| Завершить | Нужные факты результата/документ, допустимое состояние, согласованная проверка Q/R/S/T, корректная дата |
| Выдать | Все необходимые работы завершены, согласованный пакет, дата/получатель/основание, нет повторной выдачи |
| Исправить после выдачи | Отдельное право, причина, сохранение прежней версии/документов; не тихое редактирование |
| Показать общий файл | Хотя бы одна разрешённая связь и право на файл; чужие связи и их реквизиты не раскрываются |
| Выгрузить / рассчитать отчёт | Данные внутри разрешённой области; неизвестные факты не становятся нулями |
| Импортировать | Те же бизнес-команды/валидация, что в API; исторические исходные участия отдельно от новых назначений |

Условие пригодности по специальности проверяется на backend, даже если frontend заранее убрал стажёра из выпадающего списка. Нельзя получить обход через прямой POST, комиссионный состав, смену пользователя или импорт.

## 7. Экраны управления доступом

### 7.1 Пользователи

Список: логин, сотрудник, состояние входа, роли, область и последнее доступное событие входа. Отдельные действия — создать аккаунт существующему сотруднику, заблокировать, сбросить пароль, завершить сессии. Создание пользователя не создаёт повторную карточку сотрудника.

### 7.2 Роли

Список: название, назначение, активность, число сотрудников, версия. Карточка роли: модуль → отдельные действия → разрешено/нет → область. Быстрые команды выбора группы показывают, какие именно действия включат; «администратор всего» не возникает из одного неясного флажка.

Редактор позволяет создать собственную роль, скопировать существующую, изменить права/области, посмотреть затронутых сотрудников и деактивировать. Используемая роль не удаляется с потерей истории. Перед сохранением показывается разница, например «добавлено завершение чужих работ отдела 3».

### 7.3 Роли сотрудника

На карточке: выбранная роль, область/отделы, начало и окончание при наличии, основание. Можно назначить несколько ролей, прекратить одну из них или настроить срок замещения. Без отдельного права сотрудник не меняет собственные роли.

Профессии/должности и квалификации показываются рядом, но не редактируются через ролевую форму. Стажировка помечена по специальности, не значком «стажёр» на всём аккаунте.

### 7.4 Эффективные права

Проверка «Что доступно сотруднику»: действие, итоговая область, предоставившая роль/назначение и предметное ограничение. Пример: «Назначение на 13.1 недоступно: специальность находится в обучении», даже если право назначения у руководителя есть. Просмотр этого экрана не позволяет «войти под пользователем».

В обычной карточке работы сервер отдаёт `allowed_actions` и понятные причины недоступности. Фронтенд скрывает нерелевантное и объясняет полезные блокировки, но не считает это защитой прямого API-запроса.

## 8. Серверная реализация и изменения прав

Один центральный слой policy используется списками, командами, файлами, поиском, экспортами и Django Admin. Нельзя отдельно отфильтровать список, забыв карточку или download endpoint. Queryset ограничивается до пагинации и агрегатов, не после расчёта count.

Все изменения `RolePermission` и `EmployeeRole` имеют автора, время, основание и историю. Смена прав действует на следующем запросе. Если используется кэш, его версия изменяется при назначении/прекращении роли и изменении её прав; браузерные старые кнопки не сохраняют разрешение. Состояние аккаунта проверяется и для уже открытой сессии.

Начальная роль администратора доступа задаётся управляемой командой начальной настройки без встроенного общего пароля. Защита от случайного прекращения последнего действующего администратора доступа — предлагаемая эксплуатационная проверка; аварийный способ восстановления документируется отдельно. Ни пароль из старого проекта, ни демонстрационный выбор роли в шапке макета не переносятся в начальные данные.

Права администратора доступа не должны подразумевать чтение всех дел. Если владелец хочет совмещение, ему назначается дополнительная роль явно. Административная смена пароля не даёт чтения прежнего пароля.

## 9. API управления доступом

| Операция | Контракт |
|---|---|
| `GET /api/v1/me/` | Собственный профиль, сотрудник, текущие кадровые сведения, роли и доступные навигационные области |
| `GET /api/v1/permissions/` | Поддерживаемые действия, модули и допустимые области; только уполномоченному редактору ролей |
| `GET/POST /api/v1/roles/` | Реестр/создание роли; создание требует `access.roles.manage` |
| `GET/PATCH /api/v1/roles/{id}/` | Название/описание/активность, версия и последствия изменения |
| `PUT /api/v1/roles/{id}/permissions/` | Полная явная настройка прав роли с ожидаемой версией и предпросмотром различий |
| `GET/POST /api/v1/employees/{id}/roles/` | Список/назначение роли сотруднику с областью и сроком |
| `POST /api/v1/employee-roles/{id}/end/` | Прекратить роль без удаления истории |
| `GET /api/v1/employees/{id}/effective-access/` | Проверяемые эффективные действия/области и их источники, не пароль/сессии пользователя |

Пример настройки отдельного действия:

```json
{
  "permission": "expertise.suspend",
  "scope": "own"
}
```

Пример назначения роли сотруднику:

```json
{
  "employee_id": "<employee-uuid>",
  "role_id": "<department-head-role-uuid>",
  "department_ids": ["<department-3-uuid>"],
  "valid_from": "2026-10-27",
  "valid_to": null,
  "reason": "Назначение роли владельцем системы"
}
```

`valid_to: null` означает отсутствие заданного срока самого ролевого назначения, не квалификацию сотрудника и не подтверждённый бессрочный допуск. Передача пользователем произвольного массива `permissions` в обычный профиль не принимается.

## 10. Приёмка ролевой модели

- Два пользователя одного отдела с разными ролями получают разные допустимые действия.
- Один пользователь с двумя ролями работает в одном аккаунте, без выхода/входа под другой должностью.
- Начальник-эксперт завершает и приостанавливает свои назначения при соответствующих правах; чужие действия не разрешаются только из-за должности.
- Полученная 18.1 и обучение 13.1 не конфликтуют: разрешение/запрет назначения проверяется по выбранной специальности.
- Запрет стажировки сохраняется при добавлении в комиссию, прямом запросе, перепоручении и импорте новых назначений.
- Добавление права роли отражается на следующем запросе; удаление лишает действия и в старой открытой вкладке.
- Просмотр учреждения из одной роли не расширяет редактирование отдела из другой.
- Пустой список отделов у ограниченной роли не даёт весь институт.
- Прекращение одной роли не удаляет сотрудника, его документы и остальные роли.
- Экспорт, агрегаты, поиск, файлы и история не раскрывают данные вне области чтения.
- Рабочий режим/вкладка в UI не выдаёт право; сотрудник не редактирует роли запросом к своему профилю.
- Администратор доступа без отдельной бизнес-роли не получает автоматически доступ к содержимому всех экспертиз.
- Изменение ролей и квалификаций оставляет проверяемую историю; прошлые назначения не переоформляются молча.

После утверждения начальной матрицы эти сценарии превращаются в параметризованные API-тесты. Только визуального показа разных меню для приёмки недостаточно.
