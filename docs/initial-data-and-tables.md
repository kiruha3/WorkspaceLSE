# Начальные сотрудники, справочники и развитие таблиц

Версия 0.1 · 27 октября 2026 года · часть [спецификации](specification.md).

Этот перечень задаёт стартовое предзаполнение нового проекта, а не выполняет импорт или выдачу прав. Должности руководителей подтверждены владельцем. Отделы остальных сотрудников и используемые специальности сверены по первому листу локального журнала. Старый код отдела 1 не используется как нынешнее подразделение.

Это проверяемое основание предзаполнения, не правило вечного определения отдела сотрудника по любой экспертизе. В новой базе подразделения назначаются явно с датами/историей. Перевод или участие в чужой работе не меняет штатный отдел автоматически.

Статус получения каждой специальности не выводится из одного упоминания в журнале. По последнему уточнению владельца28.10.2026 ответственный может сразу выбрать «Получена», без отдельного обязательного подтверждения или основания; даты получения/срока необязательны и справочные, не ограничивают назначение. Исторические неизвестные сведения не переводятся автоматически. Будущая стажировка по новой специальности хранится отдельной строкой `training`, не отменяя уже полученных специальностей и не допуская назначения по обучаемой. В кадровой форме нельзя требовать придуманный номер удостоверения или дату лишь для сохранения известного факта.

### 1.2 Роли стартового состава

- Для начальников предлагается «Руководитель отдела» в своём отделе и «Эксперт» для собственных назначений.
- Для заместителей предлагается настраиваемая роль «Заместитель начальника отдела» плюс «Эксперт». Право назначения/перепоручения не копируется автоматически с начальника: владелец утверждает полномочия заместителя, затем они включаются в правах роли.
- Для остальных экспертов — шаблон «Эксперт», без самостоятельного администрирования справочников или ролей.
- Делопроизводитель и директор получают роли после указания конкретных сотрудников и утверждения областей; директор не получает технический `superuser` только из-за должности.
- Сотрудникам можно назначать другие/дополнительные роли и прекращать их без удаления человека и его истории.

## 2. Расширение всех справочников

Пользователь должен иметь возможность добавлять сотрудников, подразделения, должности, специальности, организации, виды документов, причины и остальные согласованные значения без выпуска новой версии фронтенда для каждой строки. Это относится к значениям бизнес-справочников, а не к произвольному добавлению новых серверных команд или неизвестных состояний процесса.

### 2.1 Единый договор управляемого справочника

Минимальные поля: стабильный ID, неизменный/управляемый код, название, описание, порядок отображения, активность, известные даты актуальности, версия, автор/время и история. Предметные поля задаются схемой конкретного справочника. У используемого кода смена смысла не выполняется простым переименованием.

Для каждого каталога предусмотрены:

1. Поиск, фильтр активности, сортировка и серверная пагинация.
2. Добавление значения и проверка дубликата/кода.
3. Изменение подписи/описания с историей и предварительным показом затронутых объектов, когда меняется смысл.
4. Деактивация вместо удаления используемого значения; исторические карточки продолжают показывать его подпись и источник.
5. Алиасы для исходных написаний при импорте без создания самостоятельных дублей.
6. Протокол слияния ошибочных дублей: подтверждение, перенос ссылок, сохранение алиасов и истории. Простое удаление ссылки не допускается.
7. Разные права чтения и изменения, при необходимости право конкретного справочника; кадровый справочник не редактируется любым экспертом.
8. Предпросмотр пакетного импорта и экспорта справочных данных; никакой прямой загрузки непроверенных кодов в рабочие записи.

31 логический каталог уже перечислен в `E:/VLSE/web-vue/docs/reference-catalogue.md`; новые каталоги можно добавлять по тому же договору. Не строить все предметные справочники одной таблицей `kind/value/json`, если теряются внешние ключи, уникальность, типы и проверяемые связи.

### 2.2 Что расширяется настройками, а что — разработкой

| Изменение | Механизм |
|---|---|
| Новый сотрудник, отдел, должность, организация, специальность | Форма управляемого справочника по правам |
| Новая роль или другой набор прав | Редактор ролей; только уже поддерживаемые сервером действия |
| Новое основание / тип письма | Справочник, если обработка использует существующий процесс |
| Новое состояние экспертизы или переход | Изменение бизнес-модели, миграция при необходимости, API-контракт и тесты; не свободная строка |
| Новая категория номера с иным расчётом | Утверждённая семантика, правила номера/отчёта, код и тесты; не просто новый option |
| Новая специальность | Значение справочника; её связь с бланком 15.1 настраивается/утверждается отдельно |
| Новая колонка существующего известного поля в UI | Настройка доступных колонок, без миграции БД |
| Новое основное учётное поле | Типизированная Django-модель, миграция, валидация, контракт и интерфейс |
| Дополнительная необязательная заметка | При обоснованной потребности схема дополнительных полей с типом, областью и версией; не замена основных полей |

Новая специальность не должна молча исчезать из отчёта из-за отсутствия строки бланка. Диагностика сообщает о ненастроенном сопоставлении, сохраняя регистрацию и её известные показатели.

## 3. Современные таблицы интерфейса

Общий компонент серверной таблицы используется для экспертиз, сотрудников, корреспонденции, файлов, ролей и справочников. Предметные редакторы остаются отдельными: единый компонент не означает одну универсальную форму на все сущности.

### 3.1 Общие возможности

- Серверные поиск, фильтры, сортировка и пагинация с устойчивым порядком и отменой устаревшего запроса.
- Видимые колонки, порядок, ширина, закрепление номера/основного реквизита и компактность. Настройки конкретного пользователя сохраняются отдельно от общей роли.
- Сохранённые представления, например «Мои в работе», «Отдел 4 — готовые к выдаче», «Октябрь по завершению». Они сохраняют фильтры, не выдают доступ.
- Общий вид может предложить уполномоченный пользователь; он не перезаписывает личный вид без явного выбора.
- Фильтры в URL, возврат к той же выборке после карточки, ясный сброс фильтров и сообщение о некорректном диапазоне.
- Раздельные неизвестное значение, ноль, отсутствие факта, загрузка и ошибка. Пустое завершение не считается датой 1899 года.
- Явный выбор области выгрузки: все найденные разрешённые записи либо страница; итоговая строка относится к выбранному полному набору.
- Переход в карточку и связанные объекты без превращения каждой ячейки в неочевидный редактор.
- Групповые действия только по поддерживаемой команде с предпросмотром и проверкой каждого объекта; массовое завершение/выдача не появляется автоматически.
- Пакетные операции не смешивают успешные и ошибочные действия без понятного протокола/оговорённой атомарности.
- Доступность клавиатурой, видимый focus, читаемые заголовки, адаптивная область прокрутки и состояния без данных.

### 3.2 Предметные колонки

| Таблица | Основные колонки |
|---|---|
| Экспертизы | Текущий номер, категория, отдел работы, специальность, действующие исполнители, поступление, срок, состояние, результат, завершение, выдача, дни по выбранному методу, признаки |
| Сотрудники | ФИО, должности, текущие подразделения, полученные специальности, обучение отдельным списком, актуальность; роли только по праву просмотра доступа |
| Специальности сотрудника | Код/название, обучение или получена, известные даты, основание, наставник при наличии, история; одна строка на отношение, не один статус человека |
| Корреспонденция | Внутренний/внешний номер, направление, вид, корреспондент, даты, тема, связь, отправка и контроль отдельно |
| Файлы | Название/исходное имя, вид, источник, копия/ссылка, версия, связи, доступность и дата добавления |
| Роли | Название, назначение, активность, число назначений, версия; права в отдельной понятной матрице |
| Справочники | Код, название, активность, период/источник, использование, история |

Сотрудник с несколькими ролями или специальностями не размножается в общем списке сотрудников. Если нужны строки участий/специальностей, это отдельное представление с явной единицей подсчёта.

Персональная настройка колонок хранится как `TablePreference` / `SavedView`: пользователь, код таблицы, версия схемы, разрешённые ключи колонок/фильтров. При исчезновении поля или прекращении права оно удаляется из применяемого вида; сохранённое представление не позволяет запросить закрытое поле. Настройки отображения не выполняют SQL и не добавляют колонки в PostgreSQL.

## 4. Развитие таблиц базы данных

Новая PostgreSQL-модель строится под предметные сущности, а не как копия плоского Excel и не как обязательная совместимость с внутренней PHP-схемой. Старые ID/строки сохраняются в связях источника для трассировки. Основные связи и ограничения — внешние ключи, уникальность текущего номера, типы, версии и индексы под реальные фильтры.

Схема развивается через версионируемые миграции Django:

1. Совместимое добавление nullable-поля / новой таблицы.
2. Проверяемое заполнение и протокол для старых строк, без вымышленных значений.
3. Перевод API/фронта на новый контракт с временным сохранением старого чтения, когда требуется.
4. Включение ограничений после проверки данных.
5. Удаление старого поля только после проверки использования, резервной копии и отдельного решения.

Например, переход «одна специальность строкой → несколько специальностей сотрудника» означает таблицу связей, сохранение источника и ручную проверку неоднозначных значений. Не следует разрезать любое упоминание в журнале на новые подтверждённые допуски. Изменение роли/должности не является миграцией схемы БД — это обычные данные с историей.

Миграции проверяются на пустой базе и на контрольной копии предыдущей версии. Отдельно проверяются ограничения PostgreSQL, сохранение исторических связей и возможность штатного развёртывания. Пользовательский редактор справочников не предоставляет произвольный `ALTER TABLE`.

## 5. Критерии приёмки расширяемости

- Уполномоченный сотрудник добавляет должность, подразделение и специальность без правки Vue-кода.
- Новая роль назначается сотруднику и начинает работать на следующем запросе без нового логина.
- Деактивированная специальность исчезает из нового выбора, но остаётся в прошлых экспертизах и отчётных снимках.
- Один сотрудник с двумя полученными специальностями и одной стажировкой остаётся одной строкой списка сотрудников.
- Пользователь настраивает колонки и сохраняет выборку, но не может добавить запрещённое поле или обойти ограничения чужого отдела.
- Миграция добавления основного поля сохраняет исходные записи и имеет контроль заполнения.
- Импорт не создаёт второй экземпляр Васильевой из падежа фамилии и не назначает нынешний АУП всем историческим работам отдела 1.
- Новое значение справочника с отсутствующим сопоставлением отчёта порождает явное замечание, а не исчезновение факта или выдуманный ноль.
