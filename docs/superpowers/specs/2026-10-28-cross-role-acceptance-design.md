# Сквозная приёмка рабочих мест

## Цель и фактическая отправная точка

Общая цель владельца — весь рабочий процесс учреждения на Django/Vue с персональными ролями и15.1 по тем же фактам. Предыдущий этап завершён коммитом0f19372: архив подключён,917 backend/345 frontend tests, рабочие472+8 записей/13файлов/996ячеек не изменились. Это progress, не повтор статуса. Отдельные HTTP tests сегодня начинают с уже подготовленных work/result/package; они не доказывают один непрерывный путь от поступления до Excel.

Следующая часть — исполняемая сквозная проверка существующей системы и исправление реально найденных дефектов. Она не подменяет оставшуюся Office-конвертацию, серверные источники, связи supplements/replaces, production-профиль, неизвестные правила выдачи или окончательную приёмку владельцем.

Владелец ранее выбрал автономное inline исполнение и передал управление; повторные approval-петли для этого технического способа проверки не вводятся. Никаких новых бизнес-политик.

## Подходы и выбор исполнителя

1. Только дополнительные API-tests: быстро, но интерфейс и фактическое переключение пользователей остаются непроверенными.
2. Вводить сценарии в рабочую БД: интерфейс настоящий, но добавляются новые факты/файлы к принятой контрольной базе; не выбрано.
3. Изолированный PostgreSQL + собранный настоящий Vue + тот же Django на одном локальном origin: выбран исполнителем. Цена — маленький тестовый runtime и один временный Python HTTP server; второй Vite/Node не нужен. UI может быть проверен с теми же данными, что HTTP-путь.

## Границы окружения

`infra/acceptance.py prepare` создаёт новую БД с уникальным именем `ais_lse_acceptance_*`, применяет текущие миграции и создаёт только искусственные личности/справочники. Пароль случайный, сведения записаны в игнорируемую `.runtime`, не в Git/stdout. Существующая БД/состояние не перезаписываются; reset/delete команды отсутствуют. `serve` повторно проверяет имя, использует отдельный media-root и слушает только127.0.0.1:8001. Сервер работает на текущем коде Django и frontend/dist; это не production-сервер.

Один WSGI-wrapper делегирует `/api/` Django, выдаёт разрешённые собранные assets и index для клиентских маршрутов. Не превращает неизвестный API/asset в HTML, не позволяет выйти из dist по пути. Секреты и реальный read-only Google источник в тестовое окружение не копируются. Запуск не останавливает текущие8000/5173/PostgreSQL. После UI-проверки остановить только созданный временный server, сохранить изолированную БД/media для повторения. В каждый момент не больше одного DB pytest.

## Сквозные факты

Общие fixtures создают пользователей, должности/роли/квалификации, а не готовые экспертизы. Разные session cookies у каждого HTTP участника. Все поступления, номера, назначения, письма, файлы, результаты, проверка/выдача создаются публичными API с CSRF, версиями и idempotency keys. Прямой ORM допустим только для начальных идентичностей/справочников и независимой сверки конечных фактов.

Основной путь: бумажное основание с поздней копией → приёмка → ручной номер → отказ стажёру → назначение квалифицированного → рабочие сведения/орган/3214=false → приостановка/запрос и согласование срока/возобновление → исходящий запрос, частичные ответы и явное закрытие контроля → сохранённый результат/завершение → платный комплект, отказ без счёта → счёт/повторная проверка/выдача → повтор команды без дубля → директор получает15.1/XLSX, находит точный вклад этой работы. Дата окончания не подменяется выдачей. Дополнительный путь: начальник действует экспертом на своём назначении; перевод получателю убирает работу из текущего списка прежнего исполнителя.

Отчётный fixture в изолированной БД имеет `is_demo=false` специально для проверки включения; это синтетический тест, не рабочие данные. Другой fixture с `is_demo=true` проверяет исключение. Цифры и ожидаемые ячейки заданы вручную, не получаются из самого расчётчика. Неполные графы честно пусты; не заявлять полный официальный15.1 из одного примера.

## Интерфейс и роли

Временные профили: делопроизводитель, начальник с собственной экспертной ролью, эксперты/получатель, стажёр, кадровик, администратор доступа, директор. Матрица — явно искусственный тестовый набор прав, не автоматическая политика для реальных сотрудников. В браузере проверить вход/выход, подходящие страницы и отсутствие чужих действий; кадровику доступен учёт специальностей, директору отчёт, начальнику назначения и своя работа. Пройти существенные действия через настоящий Vue; фиксировать отдельно, какие шаги выполнялись UI, а какие HTTP. Не называть API-сценарий полным browser E2E.

## Доказательства и завершение части

Тестовый runtime сначала проверяется RED→GREEN. Новые characterization-tests уже существующего процесса могут сразу пройти; это доказательство поведения, не выдуманный RED/исправление. Каждый найденный продуктовый дефект отдельно воспроизводится до исправления. Полная регрессия, build/check/drift/diff; один свежий итоговый reviewer и один Important fix pass без rereview.

До/после проверок live checkpoint:67 существующих бизнес-таблиц по текущим колонкам,13 файлов,472real/8demo,996ячеек+records+plan. Ни новая миграция, ни live-grant/учебные бизнес-записи не требуются. Сохраняются ветка implementation, outputs/ и .superpowers; без PHP/Googlewrites/push/merge/newworktree. Отчёт содержит точные команды, роли/шаги/пробелы, ссылки на screenshots и способ повторить изолированную проверку. Полная цель остаётся активной.
