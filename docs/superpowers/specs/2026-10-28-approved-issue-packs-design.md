# Подтверждённые комплекты СНДЗ, возврата и комиссии

## Основание и цель

Владелец подтвердил состав прямыми ответами: [решения28.10](../../owner-issuance-decisions-2026-10-28.md). Делопроизводитель должен собрать, проверить и выдать эти варианты штатным интерфейсом, а сервер — проверить документы и участников. Обычная выдача, права, история, принятые версии, оплата и отчётные факты не должны измениться.

Это следующий функциональный срез общей активной цели учреждения, не завершение всей системы. Автономное inline-исполнение и существующая ветка сохранены по ранее выбранному владельцем способу; технические решения ниже — решения исполнителя, не приписанное владельцу утверждение новой бизнес-политики. Повторные вопросы о трёх уже отвеченных комплектах не нужны.

## Подходы

1. Расширить существующий PackageItem nullable-связью с сотрудником и ограничениями. Выбрано исполнителем: проверка/выдача/неизменные редакции уже построены вокруг приложения; отдельная подписка остаётся отдельным Document. Цена — additive-миграция и расширение DTO/формы.
2. Ввести самостоятельный реестр подписок экспертов, из которого составлять комплект. Подходит при повторном использовании подписок вне выдачи, но добавляет второй жизненный цикл и правила его принятия; такого отдельного процесса владелец сейчас не задавал.

Одного текстового примечания с ФИО недостаточно: оно не обеспечивает проверяемую связь подписки с назначенным участником.

## Подтверждённые комплекты

| Подтверждённое окончание | Дополнительные обязательные приложения |
| --- | --- |
| Обычное заключение категорий1–5 | Подписка, сопроводительное; уведомление1/5; счёт2/3 либо при платностиtrue — как сейчас. |
| Акт исследования категории6 | Подписка, сопроводительное; счёт при платностиtrue. |
| Полный СНДЗ судебной экспертизы | Подписка, сопроводительное; само сообщение из принятого WorkClosure. Обычное уведомление1/5 автоматически не добавляется. |
| Без исполнения | Возвращаемые материалы/документы, описанные в составе, и сопроводительное. Подписка не требуется. |

Во всех поддержанных случаях счёт требуется для платной работы; ранее принятое правило счёта2/3 не отменено. Неизвестная платность допускается в черновике, но блокирует проверку/выдачу. Счёт не подтверждает оплату; финансовый регистр/предоплата не добавляются.

Глобальное описание возвращаемых/передаваемых материалов остаётся обязательным. Документ решения о возврате остаётся внутренним подтверждением окончания с принятым файлом, а не дополнительным обязательным выдаваемым приложением. UI должен назвать его именно внутренним основанием, не заключением. Состав передаваемых документов задаётся явно.

СНДЗ не вводится как новый результат исследований категории6: действующие правила допустимости результата не меняются. Невалидные сочетания категории/результата и отсутствие подтверждённого окончания по-прежнему блокируются.

## Отдельная подписка участника

PackageItem получает `employee = ForeignKey(personnel.Employee, null=True, blank=True, on_delete=PROTECT)`. В JSON записи — `employee_id: UUID|null`, в DTO — `employee: {id,full_name}|null`. Старые строки остаютсяnull, без угадывания человека по автору файла/имени/примечанию. Старые payload без нового поля продолжают работать для единоличной экспертизы.

Для комиссии, если комплект требует подписок, нужна отдельная строка и отдельный Document на каждого текущего назначенного участника. Участники — ExpertAssignment с ended_at=null, не все когда-либо упоминавшиеся сотрудники и не все сотрудники отдела. Закрытая работа уже запрещает штатное перепоручение; CheckWork закрепляет окончание, а неизменная PackageRevision — связи подписок с людьми. Квалификацию задним числом не переоцениваем.

Черновик комиссии допускает подписку с employee=null (в том числе старую): готовность явно сообщает о неуказанном участнике. Менее двух известных назначенных участников не превращается в единоличную работу. При проверке требуется полный состав, без лишней/устаревшей привязки, без общей подписки вместо отдельных. При возврате без исполнения комиссия сама по себе не добавляет подписки.

В новой редакции: указанный сотрудник должен быть текущим назначенным экспертом этой работы; связь с человеком допустима только у expert_subscription. Повтор роли обычного приложения запрещён как прежде; у подписок комиссии допускаются разные участники, но не повтор одного участника или одного Document для разных людей той же работы. У единоличной работы по-прежнему одна подписка, включая смешанные null/named варианты. `other` сохраняет текущую множественность.

Ограничения БД: заменить unique_issue_item_role на отдельные уникальности роли не-подписки (кромеother), безымянной подписки, именованной подписки и документа подписки в пределах revision/work; check «employee задан только у подписки». Межтабличное членство проверяется сервисом под существующей транзакцией/блокировкой. Обратная миграция не используется как способ отката рабочих данных.

## Сервис и API

Существующие маршруты/права не меняются. `required_items(work,closure,is_paid)` сохраняет сигнатуру и массив кодов, расширяет подтверждённые виды окончания. Отдельный helper `subscription_experts(work)` возвращает назначенных сотрудников комиссии. `current_facts` сохраняет4-tuple; необходимые assignments/employees и items.employee загружаются ограниченными prefetch, без N+1 по участникам.

`works[].subscription_experts` содержит толькоid/full_name назначенного состава, не кадровые сведения/логины. `content` и `content_history` сохраняют явного человека каждой строки. Диагностика может добавлять `employee_id`, чтобы показать точную недостающую подписку. Принятый полный СНДЗ берётся из closure.accepted_version; не выбирается ещё раз произвольным приложением.

Сервер возвращает новые поля всегда. Vue допускает их отсутствие до перезапуска старого backend: пустой список не означает разрешение комиссии, а null employee_id опускается из исходящего payload. Поэтому обычные формы продолжают работать во время поэтапного локального обновления; новые комиссии остаются заблокированы старым сервером. Неизвестная историческая комиссионность не приравнивается к единоличности, когда требуются подписки.

Старый null не переписывается автоматически. Добавление/смена человека — новая редакция, новая проверка. Дополнительный поздний скан не заменяет файл принятой проверки/выдачи; проверки прав выполняются и перед повтором команды. Открытая работа/чужой материал/неподтверждённый файл не обходятся новой политикой.

## Vue

В строке подписки комиссии — обязательный при проверке выбор «Эксперт» с явным пустым значением и назначенным составом. Переключение работы/роли не сохраняет несовместимого человека. Ввод и выбранные файлы не теряются при GET/403/409/потере ответа; повтор отправляет прежний захваченный пакет с тем же ключом. При обновлении списка работ доступна явная сверка новых строк платности без перезаписи введённых значений и без изменения потерянной попытки.

Карточка показывает поимённо подписки «есть/нет», принятый СНДЗ либо внутреннее решение о возврате, объяснимые blockers, историю человека и принятых файлов. Общую фразу «действия не разрешены» заменить различением недостачи, уже выданного состояния и отсутствия полномочий. Общий компонент загрузки использует нейтральное сообщение вместо события срока вне производства.

## Границы и проверка

Не входят в этот срез: частичная выдача, исправление после выдачи, изменения правил результата/комиссионности/комплекса, автоматическое создание документов и их юридическая проверка, Office-конвертация/постоянные папки/production-профиль. Они остаются общей целью; особенно отдельно проверить возможность эксперта уточнять комиссионность/комплекс после регистрации по исходному ТЗ.

Нет PHP/Googlewrites/новых автоматических grants/массового заполнения. Номера/даты/люди/старые редакции/файлы не меняются. Перед live-миграцией — backup и восстановление в новую БД с парной копией media, сравнение67старых таблиц по прежним колонкам/13файлов/472real+8demo/996cells+records+plan. Положительные выдачи — только в изолированном acceptance окружении.

Требуются RED→GREEN серверных правил/атомарности/границ, реальные HTTP-сессии, настоящие Vue-тесты с File и восстановлением, фактический браузерный прогон3новых сценариев, общие регрессии/build/check/drift, одно свежее финальное ревью и один Important fix pass. Ни обновлённые требования, ни27профильных тестов старой приёмки не доказывают эту реализацию заранее.
