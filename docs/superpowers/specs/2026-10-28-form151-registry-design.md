# 15.1 из рабочих записей АИС

Продолжение утверждённой цели: рабочий процесс Django/Vue должен завершаться отчётом по реальным данным. Предыдущий этап дал 472 реальные регистрации, сохранив фактические отделы и людей. Этот этап подключает текущие записи, а не повторно рассчитывает исходный Excel.

## Подход

Сохранить существующий расчёт по снимку для сравнения. Добавить режим registry, который собирает типизированные факты из Expertise, Receipt, HistoricalWork и принятого WorkClosure/ResultRevision. Единственная разумная альтернатива — продолжать считать только снимок — не отражает новые работы и исправления, поэтому не соответствует цели. Второй независимый калькулятор дублировал бы уже проверенные шесть разделов; общие правила агрегирования остаются одними, правила получения фактов различаются явно.

## Инварианты

- Из новых работ учитывается только принятый результат последнего подтверждения закрытия, не черновик. У исторических работ — сохранённые типизированные факты; новое подтверждённое закрытие имеет приоритет.
- Выдача не становится датой решения без исполнения. Для registry возврат с неизвестной датой остаётся неизвестным даже при отметке выдачи. Старое owner-confirmed правило предварительного снимка не меняется.
- Пустое число не превращается в ноль. Исходная опись/заметки не подменяют типизированный результат, причины и орган. Неизвестные поля перечислены как пробелы.
- Встречающиеся в БД учебные материалы получают явный Material.is_demo. Все работы такого материала исключаются из registry-отчёта. По имени, номеру, фамилии и имени пользователя система ничего не угадывает. При создании нового поступления делопроизводитель может явно выбрать учебное; по умолчанию это реальная запись. Уже созданные шесть демонстрационных работ помечаются только после проверки точных идентификаторов и резервной копии, с аудитом, без удаления.
- Режим registry требует институциональных expertise.view и reports.form151.run; выгрузка дополнительно download. Наличие этих прав не выдаёт imports.results.view и наоборот. Права не расширяются автоматически.
- Прежний API без source=registry остаётся совместимым. Веб по умолчанию показывает рабочую БД; query batch_id открывает прежний режим снимка.
- Каждое число и пробел registry содержит UUID реальных работ; веб показывает номера и ссылки на карточки, а не выдуманные номера строк Excel.
- Выгрузка проверяет fingerprint данных выбранного расчёта. Если они изменились после предпросмотра, возвращается409 и предлагается пересчитать. Ошибка не сохраняется пользователю как Excel.
- Официальный девятилистовый бланк и предварительная маркировка сохраняются. Разделы и поля, для которых ещё нет данных или правил, не объявляются заполненными. Сведения об органе для новых поступлений пока отсутствуют в модели: остаются неизвестными, имя отправителя не классифицируется догадкой.

## Границы и решения исполнителя

Без PHP, изменений Google, новых зависимостей, новых разрешений, push/merge или перемещения worktree. На текущей implementation. Продолжаем без повторного согласования уже описанной цели, согласно ранее данному поручению работать самостоятельно. Не добавляем юридические правила подсчёта причин/3214-р/повторности, которых ещё нет в проверенном калькуляторе; наличие структурированных причин в БД показываем как ещё не включённые в расчёт, а не как отсутствующие данные. Это не означает завершённую официальную форму.
