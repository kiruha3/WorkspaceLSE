# Проверяемое обновление исторического журнала

Цель: исправления нового снимка попадают в существующие работы, а не создают дубли. Предыдущий этап:472 работы,15.1 из БД; более свежий снимок содержит6 изменённых строк. Пользователь поручил продолжать самостоятельно без повторного цикла согласований; ниже решения исполнителя, не новые согласованные бизнес-правила.

Подход: отдельный пакет обновления в существующей сверке. Повторное создание отвергает номера и не решает задачу; фоновая перезапись лишает контроля и могла бы уничтожить новые факты. Общие ImportApplication/Item сохраняют протокол с action=updated, before/after и ссылкой на прежний источник, без нового вида нативного окончания.

## Инварианты

- Только origin_kind=historical, operational=False и без событий нового учёта/нативного комплекта (в том числе черновика)/подключённого основания. Импортные права не дают права переписывать рабочие документы или назначения.
- Существующие номера/категории/фактические отделы не меняются. Текущий отдел сотрудника не используется для истории.
- Сравнение трёх состояний: прежний применённый источник и сопоставление → текущие типизированные данные → новый источник и явное сопоставление. Отличие текущей записи от подтверждённой базы блокирует пакет, не затирает ручную правку.
- Пустоты/невалидные даты сохраняют прежнюю семантику нормализатора; дата выдачи не становится датой решения. Никаких новых ResultRevision/WorkClosure/Assignment/File/qualification.
- Новое сопоставление обязательно: специальность соответствует новомуM; люди выбираются явно. Состав/комплексность не меняются этим механизмом; для них отдельная процедура. Старый выбор подставляется только как редактируемая заготовка, не сохраняется автоматически; при изменении текста исполнителя люди не переносятся молча.
- Выданные по старому журналу исторические сведения допускают отдельное исправление метаданных источника с протоколом; существующая нативная MaterialIssue блокирует его. Это не изменение физического комплекта/файлов и не отмена выдачи.
- Снимки/исходные raw/facts неизменяемы. Новый источник должен быть новее применённого. Хронология обновлений остаётся в ImportApplication/Item с before/after и old/new source IDs.
- Пакет атомарен, версии работы/выбора/старый source_row проверяются под блокировками. Повтор с тем же ключом возвращает прежний протокол, другой payload409; отзыв прав действует и на повтор.
- Права существующие: institutional imports.results.view+imports.apply для записи, imports.reconcile для сопоставления. Не выдавать новые права или аккаунты.
- UI отделяет создание от обновления, показывает конкретные изменения/блокировки и протокол. В отчёте после обновления действуют новые типизированные значения; прежняя редакция выгрузки становится409.

Границы: Google только чтение, PHP/документы/ручные изменения/операционный учёт сохраняются. Не изобретать окончание468/4-6-26. Без новых пакетов, миграций схемы, push/merge/worktree. Продолжаем на implementation.

Проверка: TDD для diff/атомарности/версий/отзыва/повторов/исторической выдачи/операционного конфликта/отчёта; Vue для просмотра отличий и повторяемого обновления. После полного набора проверок и одного свежего review —backup локальной БД, явное сопоставление6 строк, применение через тот же сервис/API, независимая сверка БД/15.1, браузер и Excel.
