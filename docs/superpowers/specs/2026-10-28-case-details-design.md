# Сведения дела и управляемые типы назначивших органов

Продолжение общей цели рабочих мест и15.1. Предыдущий этап завершён наdb864f0:641 backend/253 frontend, исторические отчётные уточнения работают. В текущем состоянии новая работа не имеет места для типа органа и сведений дела; registry читает тип только из HistoricalWork. Справочники имеют API, но нет экрана управления. Исправляется сквозной путь, не меняются реальные факты владельца.

## Подход и границы

Продолжаем Django/PostgreSQL/Vue inline на implementation по поручению работать самостоятельно. Добавлять все поля к Expertise можно, но это смешивает неизменяемую регистрацию и подробности дела. Выбран WorkCaseDetails с OneToOne на Expertise, текущими предметными полями и неизменяемыми CaseDetailsRevision. Это обычные сведения карточки, не теневой калькулятор отчёта: API, карточка и registry читают их одинаково. При отсутствии WorkCaseDetails сохраняется прежнее чтение типизированной истории, без массового создания профилей.

Тип назначившего органа — AuthorityType(Reference), report_group=null|court|sk|mvd|fsb|fts|fssp|individual|legal|other. Неизвестная группа не становится «иной». Начальные коды courts_general/arbitration_courts/sk/mvd/fsb/fts/fssp/individual/legal/other следуют уже имеющимся подтверждённым меткам AUTHORITIES; код стабилен, имя редактируется, report_group выбирается явно. Старые метки сопоставляются только по точному нормализованному известному словарю, не по названию организации.

Один экран /references для существующих12 каталогов: departments, positions, specialties, sndz-reasons, unresolved-question-reasons, return-reasons, letter-kinds, letter-journals, dispatch-channels, control-closure-reasons, issue-methods, authority-types. Поиск/активность/пагинация, создание, изменение имени/активности и для AuthorityType отчётной группы, история. Code не изменяется, физического удаления нет. Журнал при создании требует направление/отдел; правило закрытия контроля выбирается при создании; уже существующие ограничения API на их изменение сохраняются.

## Данные карточки

WorkCaseDetails: expertise OneToOne, authority_type nullableFK, authority_name, official, contact, case_number, case_description, basis_text, inventory, questions_text, decree3214 nullableBool, decree_document nullableFK Document, decree_basis, created_by/created_at/updated_at. Текст вопросов не определяет автоматически Q. CaseDetailsRevision: detailsFK,number,actor,created_at,reason,before,after; unique(details,number). Снимки содержат человекочитаемый тип органа и точныйID основания, номер/состояние/фактический отдел/источник для проверки неизменности.

До первой ручной записи authority_name/official/contact/case_description/basis_text/inventory показываются из типизированной истории. case_number/questions_text остаются пустыми; номер дела из описания не извлекается догадкой. decree3214 по умолчанию неизвестно, не вычисляется из категорий1/5. При ручной очистке поле действительно становится неизвестным, а не подставляется снова из истории. Минимальное постановление/определение Receipt не заменяется текстом basis_text.

Признак3214=True требует явного пояснения и доступного документа: бумажный оригинал допустим, загруженная копия должна иметь файл. False/None не принимают основание3214. Документ можно выбрать из существующих по коду либо создать/подкрепить общей BasisDocumentForm по прежним правам. Повтор команды проверяет текущие документы и права. Полные документы читаются по своим правам, иначе restricted. В API нет смены номера/состояния/отдела/состава/людей/дат или юридического итога.

## Команды и права

GET /expertises/id/case-details/ — варианты формы по разрешённой карточке: authority_types, initial_authority_type_id, retained_authority_type_ids. Варианты не открывают кадровый каталог. ExpertiseDTO.case_details содержит текущие поля, source=typed|history|new, can_edit/edit_permission, документ и revisions.

POST тот же путь: {expected_version,reason,authority_type_id,authority_name,official,contact,case_number,case_description,basis_text,inventory,questions_text,decree3214,decree_document_id,decree_basis}, Idempotency-Key. Полный строгий пакет, reason обязателен. Material→Receipt→Expertise→существующийWorkCaseDetails→все документы→тип органа; версия после ожидания, данные+редакция+work.version+audit одной транзакцией. Повтор не дублирует. Новое неактивное значение запрещено, текущее/ранее использованное в этой истории либо точно распознанное из старого типа допускается сохранять/восстанавливать. Конкурентные источник/назначение/закрытие не смешивают факты.

Для открытой работы существующее expertise.work.update, для закрытой expertise.closed.correct, всегда expertise.view. Подтверждённый HistoricalParticipant может быть «своим» только для метаданных без нативных назначений. Это не право назначения/завершения. Наличие выданного комплекта не запрещает исправлять только эти метаданные с аудитом: документы и факты выдачи не изменяются. Новых прав, аккаунтов, live grants нет. После ручного WorkCaseDetails новый источник эту работу автоматически не перезаписывает, даже при неизменных прежних scalar-полях.

Каталоги используют references.view/manage; история только по этим правам, не по праву получать варианты формы. Добавить необязательный Idempotency-Key к прежним POST/PATCH каталогов для устойчивых форм, старые клиенты без заголовка сохраняются. Code остаётся уникальным при конкуренции, ошибка не даёт500. Повтор проверяет нынешние права, а деактивация выбранного отдела после создания журнала не ломает квитанцию успешной команды. Аудит доступен отдельным GET /references/catalog/id/history/.

## Веб и отчёт

Сведения дела в карточке видны на любом этапе, включая после перехода/выдачи; кнопка только по can_edit. Форма разделяет орган/дело/3214, сохраняет пустое и False отдельно, показывает источник и before/after. 409 сохраняет ввод и требует явно принять свежую версию; неопределённый ответ замораживает исходные path/body/key. Определённая ошибка позволяет исправить ввод, но не незаметно принять новую версию. Смена карточки/каталога не переносит поздний ответ. Созданный файл не пересоздаётся при повторе той же попытки. Обе формы используют существующие стили/адаптивность и dirty-guard.

Registry-v4 читает WorkCaseDetails вместе с прежними фактами одним SELECT. При наличии профиля его authority_type.report_group авторитетен, в том числе null; иначе прежнее точное сопоставление истории. Тип органа влияет на разделы1/5, не на категорию номера. Раздел1 P — признак3214 среди законченных обычных заключений: True1/False0/None неизвестно с адресным gap. Добавить12 клеток P только registry: всего816; journal остаётся660. Все прежние804 реальных значения сохраняются. Fingerprint учитывает профиль/группу, прежняя ссылка после изменений409. Бланк не переформатируется, форма предварительная. Причины длительности/повторность/план не выдумываются; вопрос нескольких причин задан отдельно.

Навигация показывает справочники по соответствующим правам и отчёты без ошибочной зависимости от imports.results.view, когда разрешена registry-ветка. Устаревшее сообщение главной «импорт и отчётность ещё впереди» заменяется фактическими доступными разделами, не фиктивным прогрессом.
