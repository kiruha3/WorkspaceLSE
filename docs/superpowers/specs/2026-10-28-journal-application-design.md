# Перенос актуального журнала в рабочую АИС

## Цель и основание

Перенести выбранный владельцем первый лист актуальной Google-таблицы в основной реестр Django, сохранив известные факты и неизвестность остальных. Это следующая часть общей цели полного процесса и серверного15.1, а не отдельный архив вместо рабочего реестра. Основание: общаяspec§§5/7/10, подтверждённые правила владельца, принятый предпросмотр `b35d017`. Владелец выбрал Google только для чтения; исходники PHP/VM, XLSX и Google не изменяются.

28.10.2026 проверены метаданные Google: `Лист1`,gid0,три строки заголовков;472 регистрации. Прямой CSV export этого листа на данной машине отвечает200/UTF-8 CSV,414041байт/472 номера. Это проверка доступности, не обещание автоматической синхронизации. Идентификатор источника настраивается в игнорируемой runtime-конфигурации, не в публичном seed.

## Подходы и решение исполнителя

1. Выдавать старые строки за новые приёмки/окончания: отвергнуто, пришлось бы выдумывать документы, даты и допуски.
2. Оставить их навсегда в таблице предпросмотра и отдельно считать отчёт: отвергнуто, получилось бы два реестра вместо самостоятельной АИС.
3. Основная Expertise с явно историческим происхождением и типизированными историческими сведениями: выбрано исполнителем. Просмотр, фильтры и будущий отчёт работают с тем же ID работы; вступление в новый процесс является отдельным подтверждённым действием. Цена — дополнительные проекции и проверки границы исторического/нового учёта.

Повторное согласование стека/способа исполнения не требуется по прямому «просто подними и работай дальше». Неизвестные бизнес-правила не выбираются за владельца. Исполнение inline, один итоговый независимый review, без push/merge/worktree.

## 1. Чтение Google и происхождение снимка

Только настроенный `spreadsheet_id`, цифровой `gid`, `sheet_name` и необязательный label. GET `/imports/google-source/` по нынешнему imports.results.view возвращает configured,url,sheet_name,label,spreadsheet_id,gid. Без настройки configured:false. URL формируется сервером: https://docs.google.com/spreadsheets/d/{id}/edit#gid={gid}. Произвольный URL в запросе не принимается.

POST `/imports/google-preview/` принимает reason,spreadsheet_id,gid и Idempotency-Key. Нужны оба нынешних права предпросмотра. Тело должно совпасть с текущей конфигурацией. execute_once action `imports.google_preview` проверяет receipt до обращения к Google: потерянный ответ не читает уже изменившуюся таблицу заново. Другой источник/основание с тем же ключом —409. Смена настроенного источника требует новой попытки.

Чтение через стандартный urllib, timeout20с, максимум20MiB+1; только HTTPS Google export и разрешённые HTTPS-редиректы Google, без cookies/паролей/записи/изменения sharing. Ожидаются status200 и CSV, не HTML-вход. Сетевой сбой/закрытый доступ/неверные заголовки — управляемая ошибка400 без снимка/файла/receipt. Приватный источник не публикуется автоматически; OAuth-синхронизация не реализуется под видом анонимного чтения.

ImportBatch получает source_origin upload|google_csv, origin_url (пусто у upload), source_observed_at (null у upload). CSV export содержит значения на момент чтения, а не формулы/полную структуру Google; интерфейс говорит об этом явно. Оригинальные байты CSV, их хеш, raw и диагностика сохраняются существующей границей. Функция записи снимка переиспользуется без вложенного второго execute_once. Старые снимки не переписываются.

## 2. Исторические работы в основном домене

Expertise.origin_kind=native|historical, default native. appointment_nature, is_commission и specialty допускают null только при historical; для native DB constraint и нынешний API по-прежнему требуют известные значения. null не изображается первичной/единоличной или выдуманной специальностью. ComplexGroup остаётся предметной связью; неизвестность комплекса отмечена отдельно.

Уточнение по настоящему источнику: свежий разбор472 строк показывает4 строки с ошибками: пустой M у470/471/472 и T=`1НПВ` у384. Ошибка неключевого отчётного поля не должна исключать целую регистрацию. Применение блокируют неопределённая/дублирующаяся идентичность B, отсутствующее/недопустимое поступление C и неизвестное состояние D, а также несопоставленный отдел. Прочие недопустимые значения остаются null с диагностикой происхождения. Дата P раньше C не становится концом; конфликт вида результата и категории не становится достоверным result_kind. Непустой признанный код M связывается только с тем же кодом справочника; отсутствующий/непризнанный M допускает null или явно выбранную ответственным специальность с основанием. Общее число зарегистрированных работ не уменьшается из-за недостающего M/T.

Receipt.status получает historical: это перенос строки журнала, не подтверждённая приёмка. Дата received_at всё ещё обязательна: строка без допустимого C остаётся на сверке, дата не подставляется. Basis_document=null допустим у historical, при этом Document и FileVersion вообще не создаются. Material на первом переносе — явно исторический контейнер данной регистрации; одинаковая опись не объединяет материалы автоматически. Явный complex_group_key в подтверждённой выборке объединяет материалы и создаёт группу; одна специальность не повторяется в группе, номер у каждой работы собственный. Для неизвестной группировки complex_known:false.

Новая модель `HistoricalWork` OneToOne Expertise, FK ImportRow(PROTECT), actor/created_at/reason, operational:false. Типизированные поля: result_kind, completed_on, return_decided_on, issued_on, complexity_level, questions,categorical,probable,unresolved (все nullable), amount Decimal(nullable); authority_type,authority_name,official,contact,basis_text,case_description,inventory,executor_raw,unresolved_note,unresolved_reason_raw,notes,delivery (Text); complex_known, suspension_history_complete(defaultfalse), statistics_confirmed(defaultfalse). Исходные raw/formulas/extra остаются только в неизменяемом ImportRow, не заменяются этим слоем.

Историческое completed_on берётся из разобранного P только для completed. return_decided_on из произвольной P/выдачи не выводится. issued_on — только ранее распознанная фактическая отметка, без MaterialIssue. ResultRevision/WorkClosure/Suspension/ExpertAssignment не создаются ради заполнения обязательных полей нового процесса. Исторический результат является фактом своего происхождения, не фиктивным подтверждённым файлом.

`HistoricalParticipant` связывает HistoricalWork и существующего Employee (unique), только по явному выбору ответственного. Имя из L не создаёт сотрудника, логин, роль, квалификацию или живое назначение. До первого настоящего назначения подтверждённая историческая связь участвует в фильтре сотрудника и собственном read-only просмотре. После появления настоящих назначений текущий список определяется ими; бывший исторический исполнитель не остаётся получателем. Запись чужого участника не открывает expert-действия.

## 3. Проекции и ограничения

Expertise DTO добавляет origin_kind и historical:null|HistoricalDTO. Исторический DTO содержит перечисленные типизированные факты, current_participants, source:{batch_id,row_id,source_row,origin_url,source_observed_at}, operational,composition_known,report_gaps. Он не выдаёт общий source URL или raw-снимок пользователю без imports.results.view. Разрешённая карточка работы может показать необходимые факты происхождения, не весь смешанный источник.

Карточка/реестр показывают исторические сведения, неизвестные признаки, отсутствие электронного основания и отдельную фактическую выдачу из журнала. Старый текст исполнителя подписан «в источнике»; подтверждённая связь с сотрудником — отдельна от настоящего назначения.

Production: календарные дни используют received_at и настоящий конец из WorkClosure, иначе известный исторический completed_on/return_decided_on. У открытой работы конец — текущая дата; у закрытой с неизвестным концом calendar_days=null. Если историческая полнота пауз не подтверждена, paused_days/active_calendar_days=null даже при известных календарных днях. SQL-фильтр календарных дней использует ту же границу, не считает закрытую работу до сегодня. Нулевая сумма пауз не означает, что история известна.

Пока operational:false, живые назначения/производство/результат/корректировка закрытия отклоняются управляемо; UI не рекламирует эти действия. Это проверяется на сервере, не только скрытием кнопок. Переписка и подкрепление реальных документов возможны по собственным правам и не меняют исторические факты автоматически. Выдача требует настоящего подтверждённого WorkClosure и принятого комплекта; историческая дата выдачи дополнительно блокирует повторную выдачу/изменение выданного материала.

`historical_facts(work)` — стабильная предметная проекция для следующего Python15.1: если появился подтверждённый новый результат/закрытие, приоритет у него, иначе известные исторические факты с происхождением и пробелами. Один ID регистрации считается один раз. Неизвестная специальность не исключает регистрацию из известных общих показателей, но блокирует достоверную разбивку по специальностям. Сам калькулятор15.1 и выгрузка являются отдельным следующим планом, не имитируются этой проекцией.

## 4. Сверка и атомарное применение

Права institution-only: imports.reconcile (явно выбирать сопоставления), imports.apply (применять), imports.history.activate (подтверждать вход в новый процесс), дополнительно imports.results.view. Реальные роли не расширяются. Явный DEMO opt-in добавляет только новые права делопроизводителю и отказывает роли с неучебным участником, без восстановления иных отозванных прав.

GET `/imports/{batch}/reconciliation/` возвращает строки постранично с фильтрами search,classification(new|unchanged|changed|invalid),page. Каждая строка: исходный RowDTO, существующая работа с тем же каноническим номером (только краткий id/number/version), classification, blockers, suggested department/specialty по точному коду, confirmed selection либо null. Это не поиск человека по приблизительной фамилии. Отсутствующие/неактивные коды явно требуют выбора/создания справочника отдельным разрешённым действием, код1 не превращается в3/4 по фамилии.

GET `/imports/reconciliation-options/` по reconcile даёт только id/code/name отделов/специальностей (включая inactive для истории) и id/full_name/is_active сотрудников. Не раскрывает учётные записи/HR-профили и не подтверждает допуск. Выбранный Department.code должен совпадать с разобранным кодом; Specialty.code — с признанным M, а неизвестный M допускает отдельный явный выбор или null. Произвольное исправление номера не маскируется подбором иного отдела.

PUT `/imports/{batch}/rows/{row}/selection/` по reconcile + reason/key, expected_version сохраняет отдельный `ImportSelection` (unique row,version1+) с department,specialty,employee_ids,appointment_nature:null|primary|repeated|additional,is_commission:null|bool,complex_known:bool,complex_group_key:null|string,statistics_confirmed:bool. Raw/нормализация не редактируются. Для неизвестного назначения явно null; признаки не проставляются эвристикой. statistics_confirmed:true допустим только при Q/R/S/T известных и сходящихся. Группа требует complex_known:true; комиссия требует не менее двух явно выбранных участников, если подтверждается состав. Неизвестный состав допускает перенос с пробелом, не даёт operational.

POST `/imports/{batch}/apply/`: reason,key, selections:[{row_id,expected_selection_version}]. Только явно выбранные строки, максимум1000, distinct. Команда получает advisory-lock по всем каноническим номерам в сортированном порядке, затем locks batch/selections/references в фиксированном порядке; текущие права и версии проверяются повторно. Ошибка любой строки откатывает весь выбранный пакет.

Создаются Material/Receipt(historical)/Expertise(historical)/HistoricalWork/participants и `ImportApplication`+`ImportApplicationItem` (unique source row). Известные поля копируются, неизвестные остаются null, grouping только явный. Ничего не создаёт документы/квалификации/живые события. Существующие канонические номера не создают дубль: тот же уже применённый row возвращает прежнюю связь, новый снимок с тем же номером показывается unchanged либо changed. Автоматических updates по совпадению номера нет. Изменённый новый источник требует отдельного подтверждённого обновления с контролем локальных правок в следующем расширении; отказ содержит конкретный конфликт, не молчаливый пропуск. Номер строки не становится вечным ID Google.

Receipt команды хранит только application/event IDs. Повтор после потерянного ответа и отзыва права не обходит отзыв; другое тело409. API возвращает `{event:{id},application:{id,batch_id,created_count,existing_count,items:[{row_id,expertise_id,action}]}}`; GET `/imports/applications/{id}/` читает протокол по results.view. Apply Available включается только после готовности этой операции и отдельного права; не означает, что все строки готовы.

В первой версии исправление исходных ошибок выполняется владельцем в Google и новым снимком, а не скрытым перезаписыванием raw. Ошибочная строка может остаться на сверке, не исчезает из сводки. Первое реальное применение оператор подтверждает через UI; разработчик не принимает неизвестные признаки за владельца и не применяет472 строки автоматически.

## 5. Подтверждение продолжения исторической работы

POST `/expertises/{id}/activate-history/`, reason/key/expected_version, basis_document_id,appointment_nature,is_commission,complex_known:true,complex_group_id:null|UUID, specialty_id (обязателен, если раньше неизвестен; известная специальность здесь не заменяется),suspension_history_complete:boolean,past_suspensions:[{suspended_on,resumed_on,reason}], плюс для suspended открытый suspended_on; для закрытой — result либо return-data как у существующего подтверждения. Требуются imports.history.activate и expertise.register в области работы, expertise.view, отдельное documents.view на выбранные документы. Состав/комплекс и специальность должны быть явно известны. Эта операция не подтверждает квалификации.

Под lock Material→Receipt→Expertise проверяются отсутствие настоящей/исторической выдачи, версия и historical operational:false. validate_basis проверяет реальный указанный документ, не создаёт его. Для in_progress после подтверждения Receipt.accepted/operational:true можно обычным начальником назначить квалифицированных участников. Для suspended неизвестная дата начала не подставляется: нужен подтверждённый открытый интервал, непересекающиеся прежние интервалы; при неполной истории active-days остаются неизвестными. Для completed/without_execution создаётся первое настоящее подтверждение закрытия с настоящим итоговым файлом/датой через существующие валидаторы, не подмена исторических исходников. Тип закрытия не меняется.

Участники исторического источника сохраняются как происхождение; новое назначение проходит обычную проверку qualified/training/valid_until. Для подтверждённой комиссии квалификация нужна каждому участнику. Позднее исправление результата идёт существующей отдельной процедурой; выданная работа не корректируется этой кнопкой. Известная историческая выдача не становится повторной новой MaterialIssue.

## 6. Интерфейс

В `/imports` — настроенный Google-источник и кнопка «Проверить актуальную Google-таблицу», явное только-чтение/CSV-значения, неизменный reason/key при повторе, dirty/latest guards. Файловая загрузка сохраняется.

В снимке — переход «Сверить и перенести». Страница `/imports/:id/reconciliation`: количество новых/совпавших/изменённых/ошибочных для всего снимка, URL-фильтры/пагинация, выбор строки и редактор сопоставления, неизвестные признаки по умолчанию, явное сохранение выбора. Множественное применение только сохранённых selections с отображением номеров/количества и подтверждением причины; loading/conflict/error/success. Никаких действий на Google или автосоздания сотрудников. Протокол содержит ссылки на настоящие `/expertises/:id`, возврат сохраняет фильтры.

Карточка исторической работы показывает источник и текущие факты/пробелы, подтверждённых исторических сотрудников, известную/отсутствующую выдачу; не предлагает фиктивное завершение. Отдельная форма подтверждения продолжения требует реальные документы/признаки/даты. Права текущей роли проверяются заново на каждом запросе, session flags рекламируют только реализованные команды.

## 7. Приёмка

Тесты чтения Google: fixed host/id/gid, headers/limits/network/access, no snapshot on failure, cache before second GET, config change/current rights. Тесты schema/native invariants и проекций (null/date/filter/participants). API сверки/пакета: unknown не false/0, no business writes до apply, nofake документов/событий/квалификаций, atomic rollback/conflict/concurrency/differentbody/revocation/inactive refs/grouping. Activation: live workflow validators, explicit historic dates, trainee denied by subsequent assignment, issued guard, повтор/версии.

Vue: exact DTO/body, pending/retry, selection versions/dirty guard, filters/global counts, no old source under new route, absent capability/right, historical display/activation gates. Полные backend/frontend/type/build gates, один fresh review и один TDD fix-pass, настоящий браузер с DEMO apply→рабочая карточка→подтверждение→назначение→производство. Чтение реального Google и сохранение его предпросмотра разрешены; массовое бизнес-применение требует операторской сверки. Общая цель остаётся активной для15.1, документов, незакрытых политик и финальной приёмки всех ролей.
