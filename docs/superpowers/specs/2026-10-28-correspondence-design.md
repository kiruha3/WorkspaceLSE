Владелец поручил продолжать реализацию без повторных циклов согласования выбранного Django/Vue подхода. Общая цель включает выдачу, импорт и15.1; этот срез её не подменяет.

## Выбор и границы

Выбран отдельный correspondence Django-модуль в существующем монолите, единый реестр/карточка Vue и блок переписки в экспертизе. Повторное использование таблицы экспертиз или JSON-поля «вся переписка» смешало бы независимые номера/даты и доступ; отдельная почтовая система не нужна для ручного делопроизводства. Существующие сессии, ролевые scopes, execute_once, документы/версии и аудит сохраняются. Без новых зависимостей, серверов, worker, VM, push/merge.

Поддерживаются самостоятельные письма, связь с материалом и несколькими работами, запрос→несколько частичных/дополнительных/завершающих ответов обоих направлений. Регистрация, фактическое получение, отправка адресатам, подтверждённая доставка и контроль — отдельные факты. Никаких реальных email/внешних судебных отправок. Прикрепление имеющихся/новых документов использует файловый модуль; URL/папки/office-conversion остаются общей последующей задачей, не выдаются за реализованные.

Технические решения этого среза: ручной свободный внутренний номер в настраиваемом журнале, уникальный в журнале и году регистрации. Журнал имеет direction и optionaldepartment. Направление/journalnamespace — семантические поля, не произвольные статусы. Владельцу задан async-вопрос: единый журнал учреждения или по отделам. До ответа реальных журналов/номеров не переносим, учебная демонстрация использует явно учебные журналы. Первоначальные incoming/outgoing журналы — настраиваемая возможность, не утверждённый регламент.

Данные корреспондента/адресатов пока сохраняются типизированными фактами имени/адреса/email, без выдуманных реквизитов организации. Общий Organization/Contact справочник остаётся частью общего завершения проекта, позднее добавит nullableFK рядом с сохранёнными фактами, не сотрёт их. Печать журналов/писем по утверждённым шаблонам и корректировка зарегистрированных реквизитов — отдельные следующие работы; текущая регистрация замораживает содержание, отправку/получение/контроль/поздние файлы это не блокирует.

## Модель и факты

- Letter: UUID, фиксированное incoming|outgoing, department?, responsible?, created_by, created_at, version, current_revision?.
- LetterRevision: append-only number/actor/created_at/reason, kindFK, subject, body, sender_name, external_number, external_on?, document_on?, received_on? (известный факт для входящего при подготовке), note, material?, parentLetter?, reply_completeness:null|partial|additional|final; expertises M2M. Parent задаётся при создании и не меняется; родитель должен быть зарегистрированным, читаемым и противоположного направления. Draft save создаёт новую редакцию; после регистрации обычное изменение содержания запрещено.
- LetterRecipient: revisionFK, name, address, email; один или несколько. Нет автоматической валидации произвольного названия суда как email. Для исходящего регистрации нужен хотя бы один адресат; для входящего — sender_name; тема обязательна при регистрации, не обязательно в промежуточном черновике.
- LetterAttachment: letter/document unique, added_by/time/reason. Подкрепление после регистрации разрешено отдельным letters.attach; не изменяет содержание и не переписывает доказательства прежних событий. Обычное добавление версии файла не означает повторную отправку.
- LetterRegistration: one-to-oneLetter, revisionFK, journalFK, registration_number, registered_on, year, actor/time/reason; unique(journal,year,number). Внешний номер не подставляется во внутренний. Неизвестное received_on не равно registered_on. LetterRegistrationFile: registration/fileVersion unique — снимок реально имевшихся вложений; поздний файл не попадает в него задним числом.
- LetterDispatch: letter, sent_on, channelFK, tracking, comment, evidenceDocument?, acceptedEvidenceVersion?, actor/time/reason, recipients M2M из зарегистрированной редакции. Можно фиксировать фактическую отправку части адресатов, повторную отправку отдельным событием; state partial/sent вычисляется по покрытию адресатов, не одним флажком. LetterDispatchFile хранит снимок отправленных на этот момент версий вложений. Отправка требует регистрации исходящего и непустого набора адресатов, не до регистрации/даты документа и не в будущем. Бумажное письмо допускает отсутствие электронной копии, не выдумывает файл.
- LetterDelivery: dispatchFK, recipientFK, delivered_on, evidenceDocument?/acceptedVersion?, actor/time/reason; unique(dispatch,recipient), дата от отправки до сегодня. Не выводится из отправки.
- LetterReceipt: incoming registeredLetter, received_on, evidence?/acceptedVersion?, actor/time/reason; один подтверждённый факт, повтор только тем же ключом. Может предшествовать регистрации, но не дате документа и не быть будущим. При регистрации известное draftreceived_on создаёт этот факт; null остаётсяnull. Уточнение ошибочного подтверждённого получения требует будущей отдельной процедуры, не тихого overwrite.
- LetterAssignment: старый/новый ответственный, actor/time/reason. Назначение не равно назначению экспертом и не требует экспертной квалификации; активность сотрудника и область проверяются. Создатель не сохраняет собственный доступ навсегда после перепоручения.
- ControlTask: one-to-oneLetter, opened_on, due_on?, due_basis, version; требуется только по явному действию, не из kind=request/information. Letter responsible — текущий ответственный и по контролю, не дублирующий независимый owner. ControlEvent: opened|deadline_changed|closed|reopened, actual_on, due_on?, due_basis, closure_reasonFK?, replyLetter?, comment, actor/time/reason. Текущее закрытие — последний closed, отменяется только явным reopened, история сохраняется. Просроченность вычисляется из due и текущей даты, не редактируется как постоянный статус.

Справочники: LetterKind(request/reply/information/other/extension_motion/notification/cover_letter), DispatchChannel(email/russian_post/in_person/edi — только ручной учёт), ControlClosureReason(reply_sent/reply_received/request_withdrawn/no_reply_required/other), LetterJournal. Название/активность/версия по существующему Reference договору, коды стабильны. ClosureReason имеет фиксированное rule:reply_sent|reply_received|withdrawn|not_required|other, новое произвольное значение по умолчаниюother требует пояснения; реальная отправка/полнота не определяется изменяемым названием. Seed сохраняет правки и деактивацию, журнал учёта не заполняет.

Для закрытия reply_sent: исходный входящий, явно связанный завершающий исходящий ответ, зарегистрирован и фактически отправлен всем его адресатам до closed_on. Для reply_received: исходный исходящий, завершающий входящий ответ, зарегистрирован и имеет известное получение до closed_on. Частичный/дополнительный ответ не удовлетворяет этим двум основаниям. Withdrawn/not_required/other — явное самостоятельное решение с комментарием. Смена срока не является возобновлением; reopened отдельное право/причина. Завершение экспертизы не меняет контроль.

## Права, связи и блокировки

Все чтения требуют letters.view; списки и агрегаты ограничиваются до пагинации. Own на чтение: текущий responsible либо действующее участие в связанной работе с expertise.view. Own на изменение: только responsible; наличие одной видимой связанной работы не даёт менять всю общую переписку. Department/institution действуют по области конкретного действия, не по наиболее широкой другой роли. В DTO связанные работы/материалы/ответы фильтруются отдельно, недоступные реквизиты не раскрываются. Parent при утрате права — только{id,restricted:true}; нет скрытых counts.

Новые действия: letters.reply, letters.attach, letters.mark_received, letters.mark_delivered, control.view, control.assign(departments/institution), control.reopen. Существующие letters.draft/register/mark_sent/view иcontrol.close используются без изменения смысла. Черновик ответа требует letters.draft иletters.reply. Назначение другого responsible и установка/изменение контроля требуютcontrol.assign. Никаких автоматических добавлений в уже настроенные реальные роли; актуальные стартовые шаблоны только новым ролям, явный --enable-correspondence только стабильным учебным ролям при отсутствии неучебных участников.

Создание/замена набора связей требует чтение всех выбранных работ/материала и letters.draft в области каждой работы; материал читаем через разрешённое поступление или работу. История прежних недоступных связей не раскрывается в карточке. Минимальные options сотрудников не выдают кадровые сведения; выбор другого responsible толькоcontrol.assign и по области. Старый responsible/эксперт после передачи не получает replay-доступ через сохранённый key.

Документ читается через разрешённую связь письма только вместе с documents.view в той же области; это не даёт upload. Нет раннего отказа из-за отсутствия expertise.view для самостоятельного письма. Прикрепление существующего документа требует его чтения; снимки событий явно указывают принятые FileVersion, поздние bytes не меняют подтверждённое. Внешняя ссылка на parent сама не расширяет scope.

Все мутации reason+expected_version+Idempotency-Key (create без expected_version). Кэш минимальный event/letterID, ответ свежий с нынешними правами/редакцией/редакцией доступа к файлу. RootLetter/связанный parent или reply блокируются в порядкеUUID; документы всей команды в едином порядкеUUID до справочников. Контроль/письмо сериализуются общей Letter блокировкой. Даты учреждения, не автоматические нормативные сроки; неизвестные даты остаютсяnull.
