# Специальности: необязательное подтверждение и справочные даты

Владелец28.10.2026 попросил убрать обязательное подтверждение и оставить даты по специальности справочными. Это уточнение заменяет прежнее требование обязательного основания при неизвестной дате и проверки даты/окончания срока при новом назначении. Статус обучения остаётся запретом назначения по обучаемой специальности. Исторические неизвестные сведения не превращаются в полученную специальность автоматически.

## Подход

Оставить обязательное подтверждение, но скрыть его в UI, нельзя: сервер продолжит блокировать работу. Автоматически перевести все старые специальности в полученные тоже нельзя: владелец этого не просил. Выбран прямой учёт статуса «Получена» уполномоченным пользователем без обязательного документа/основания/даты; даты сохраняются для справки. Стек, текущие права и модель сохраняются, миграций и массового изменения данных нет. Продолжается ранее выбранное автономное inline исполнение без повторных approval-петель, безpush/merge/worktree.

## Контракт

- `qualification_eligibility(employee,specialty,at,qualification=...)`: активные сотрудник/специальность и явный status=qualified дают допуск, независимо от пустого basis, qualified_at или valid_until. Training, unknown_legacy, отсутствие специальности и неактивность по-прежнему запрещают. Аргумент at сохраняется для совместимости вызовов; даты больше не являются временной политикой допуска.
- POST `/employees/:id/specialties/`: status принимает training/unknown_legacy/qualified; qualified_at nullable необязателен, как и basis. Для qualified требуется существующее `specialties.qualify`, для других статусов — `specialties.training.manage`, в области именно этого сотрудника. Сначала блокируется Employee; дубли и неактивные ссылки отклоняются.
- Старый POST `/employee-specialties/:id/qualify/` сохраняется для явного перевода обучения/исторической записи в «Получена», но basis необязателен. Уже полученную специальность повторно не переводит, version409 остаётся.
- Новый PATCH `/employee-specialties/:id/` меняет только справочные training_started_at/qualified_at/valid_until/basis, с expected_version; не меняет status/сотрудника/специальность/наставника. Полученная требует specialties.qualify; остальные — specialties.training.manage. Row lock, актуальные права, before/after audit, version+1. Пустой PATCH, лишние поля, невалидные даты и окончание до получения дают400 без записи; stale409. Получение/срок могут быть неизвестны и явно очищаться; существующие даты не стираются от пропущенного поля. Порядок пары дат остаётся проверкой согласованности сведений, не правилом допуска.
- В UI можно сразу добавить «Получена» при соответствующем праве; без этого права доступно только обучение/неизвестные исторические сведения. Даты и основание необязательны. Старое действие называется «Отметить полученной», не требует отдельного подтверждающего основания. У всех статусов доступно редактирование справочных сведений по соответствующему праву, без превращения обучения в квалификацию.
- Не терять несохранённое ФИО при сохранении специальности; dirty guard сравнивает ввод с начальным, а не считает загруженные даты правкой. Ошибки403/409 сохраняют форму. Изменение метаданных специальности не меняет прошлые снимки назначений, работы, роли, отчёт или исходный журнал.

## Приёмка

Сначала RED на прямом создании qualified без даты/basis, старом qualify с пустым основанием, справочных датах и PATCH. Проверить реальные candidates+assignments: пустое основание/будущая дата/прошедший срок не запрещают, training/unknown/inactive запрещают, snapshot сохраняет исходные сведения. API права/границы/дубли/неактивность/атомарность/версия/аудит. Vue реальных форм: прямое создание, только-разрешённые состояния, необязательные поля, редактирование дат и очистка без изменения статуса/ФИО, ошибки и dirty.

Один свежий final review и один RED→GREEN исправительный проход Important, без повторного ревью и попутных Minor. Полный backend последовательно в test_ais_lse, frontend/typecheck/build/check/drift/diff. Live: только просмотр существующих сотрудников/форм, никаких изменений реальных квалификаций или выдачи прав; положительные записи проверяются изолированным HTTP/Vue. Реальная БД, файлы и996значений/происхождение отчёта остаются прежними. После проверки перезапустить только существующий Django; Vite один. Общая цель процесса остаётся активной.
